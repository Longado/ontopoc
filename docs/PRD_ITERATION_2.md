# OntoPoc 迭代 2 需求：换数据不改代码，复核能回流

> 状态：待开发。起草 2026-09-13，基线 main `1fc0f08`。本文是当前唯一的迭代计划；`superpowers/plans/2026-09-13-improvement-roadmap.md` 与 `2026-09-13-nhtsa-shortcomings-and-next-rounds.md` 转为历史记录。

## 1. 现状

迭代 1 交付了一个能用的召回范围研判工具，数据只有一份：NHTSA 雪佛兰 Bolt EV / EUV 2017–2023，13 个召回、679 条投诉。系统自动搭建本体并由代码核验，名称对应补回刹车召回的 34 条候选，13 个召回都有模型初判；页面分本体、召回、复核、结果四个标签页，复核即标注，结果可下载。

两个问题没有回答：

1. **它是不是只对这一份数据有效？** 只跑过一个品牌；页面页头、页面数据的文件地址、打包脚本的默认输出名都写死了这份数据。
2. **真人复核之后，能不能马上得出结论？** 下载文件现在没人接：不能汇入样本库，也没有脚本能比较"规则、模型、规则加模型"三种做法谁更接近人。真人试用那天拿到的标注，只能手工去看。

## 2. 本轮目标

从"一份数据的演示"变成"可复用、可校准的研判工具"：

- **G1 复用**：换一个品牌车型，从取数到页面不改代码；页面能在两份数据之间切换。
- **G2 校准就绪**：真人复核一回来，当天就能跑出三种做法的对比和"模型这一步留、改、还是去掉"的依据。

**本轮不做**：企业数据；账号与多人协作；静态站部署（待用户决定，见第 8 节）；模糊匹配或实体消解引擎；任意问题的通用本体平台；页面英文版；调提示词（没有人工标注之前不改）。

## 3. 用户与场景

- **质量工程师**：打开页面，选数据集和召回，逐条复核范围外投诉，下载结果。
- **FDE / 用户本人**：拿第二份数据给潜在客户演示"换一家车企也能跑"；试用结束后把复核文件交给系统，拿到对比结论。

## 4. 需求

优先级：P0 本轮必须完成；P1 本轮做，可随 P0 之后；P2 有空再做。

### R1 数据集说明从数据里读（P0）

快照记录这份数据的范围：品牌、车型、年款区间、取数时间；页面页头、页面数据文件名、打包脚本的默认值都从这里来，不再写死"雪佛兰 Bolt"。

验收：
- `fetch_nhtsa_snapshot.py` 生成的快照带 `scope`（品牌、车型列表、年款区间）；现有 Bolt 快照补上这项，不重新取数。
- 复核页页头显示的数据说明来自页面数据；`git grep` 复核页和页面逻辑源码里不再出现 "Bolt" 字样。
- 打包脚本按快照生成输出文件名（如 `nhtsa-chevrolet-bolt-ev-bolt-euv-2017-2023.json`），不再用写死的默认名。
- 首页 `/landing` 的"验证"一段是对外宣传，保留 Bolt 的数字，不在本需求范围。

### R2 第二份数据跑通（P0）

测试数据：**现代 Kona Electric 2019–2021**。2026-09-13 实查：2019、2020 款各有 3 个召回，部件含电气系统与液压刹车，投诉分别 54、185 条。刹车召回与 Bolt 一样写作 "SERVICE BRAKES, HYDRAULIC"，正好检验名称对应在另一家车企上是否同样成立。

验收：
- 取数 → 在线运行 → 打包 → 页面，全程不改代码；如果必须改，交付一份改动清单，逐条写明改了什么、为什么是这份数据逼出来的。
- 记录本次运行的事实：本体提交次数与被退回的原因、模型提出与被拒的名称对应、每个召回的候选数与三类分布、未进入任何候选的投诉数。
- 与 Bolt 结果并排写一段对比：两份数据上相同与不同的地方。

### R3 页面切换数据集（P0）

页面数据目录下有一份数据集清单；复核页页头能切换数据集；每份数据的复核各自保存，互不干扰。

验收：
- 清单文件列出每份数据的名称、页面数据地址、召回数、投诉数、取数日期，由打包脚本生成或更新。
- 在 Bolt 与 Kona 之间切换：标签页、召回选择、复核标记都按数据集分开；刷新后回到上次选的数据集。
- 某份数据读不到或格式不对时，只提示这一份，其他数据照常能用。

### R4 复核回流为样本库（P0）

下载的复核文件可以交给脚本汇入仓库里的样本库，成为以后比较提示词和做法的固定样本。

验收：
- `scripts/import_reviews.py --input <下载文件> --reviewer <姓名或代号>` 把复核逐条写进 `examples/labels/<数据集>.jsonl`：投诉编号、所属召回系列、人工结论、备注、模型结论与提示词版本、复核人、复核时间、本体哈希。
- 本体哈希与当前页面数据不一致时拒绝导入并说明原因；同一复核人对同一条投诉重复导入时保留最新一次，并在输出里列出被覆盖的条目。
- 样本库文件入库前检查不含本机路径和密钥。

### R5 三种做法对比（P1）

在样本库上比较：只用规则、只用模型初判、先规则筛再看模型。规则写在代码里、作为基线，不调参。

验收：
- `scripts/compare_judgments.py --labels examples/labels/<数据集>.jsonl` 输出一张表：每种做法与人工一致的条数、判错的条目（分"该判是却判否"与"该判否却判是"），以及样本数；样本少于能下结论的量时如实写明，不给百分比外推。
- 规则定义与迭代 1 的对比实验一致：投诉标了起火，或原文出现 fire / smoke / burn / flame / thermal / melt。
- 离线测试用手工构造的样本文件验证计算正确；真实结论只在有真人标注后产生。

### R6 复核人留名（P1）

样本需要知道是谁标的。页面"结果"页可以填写复核人（本机保存），下载文件带上它；R4 导入时命令行参数优先。

验收：填写后刷新仍在；下载文件每行带复核人；不填也能下载，导入时必须补上。

### R7 小项（P2）

- 网站 favicon 与 GitHub 社交预览图，从像素 Logo 切。
- 清理 GitHub 上已合并的旧分支，只留 main、开发分支和归档标签。
- 更新"现状与路线"网页的截图为新版界面。

## 5. 非功能要求

- 不引入新依赖；每个模型调用带提示词版本、temperature 0；先写失败测试再实现，改已有测试单独提交。
- 数据来源可追：快照记录请求地址与取数时间，清洗规则和删除条数写进快照；本体、数据、页面用哈希锚定。
- 公开仓库：推送前查本机路径、个人信息、客户名与密钥。
- 页面在 1440 宽和 390 宽下都能用，没有横向溢出。

## 6. 里程碑

## 7. 风险

- **Kona 的投诉接口可能不完整**：Bolt 2017 款只返回 4 条投诉就是先例。R2 要记录每个年款的返回条数，异常的如实标注。
- **模型在新数据上搭出不同的本体**：这正是要检验的；只要通过核验就接受，差异写进对比。
- **一次试用的样本量小**：30 分钟大约几十条，只够看方向，不够给准确率。R5 的输出必须写清样本数。
- **用户找人的时间不确定**：M1、M2 不依赖它，先做完；M3 等人。
