# OntoPoc 迭代 2 需求：换数据不改代码，复核能回流

> 状态：M1、M2 已完成（2026-09-13 / 09-14），模拟用户试用后的修正已完成（09-14，见第 11 节），M3 等用户找人试用。起草 2026-09-13，基线 main `1fc0f08`。本文是当前唯一的迭代计划；`superpowers/plans/2026-09-13-improvement-roadmap.md` 与 `2026-09-13-nhtsa-shortcomings-and-next-rounds.md` 转为历史记录。

## 1. 现状

迭代 1 交付了一个能用的召回范围研判工具，数据只有一份：NHTSA 雪佛兰 Bolt EV / EUV 2017–2023，13 个召回、679 条投诉。系统自动搭建本体并由代码核验，名称对应补回刹车召回的 34 条候选，13 个召回都有模型初判；页面分本体、召回、复核、结果四个标签页，复核即标注，结果可下载。

两个问题没有回答：

1. **它是不是只对这一份数据有效？** 只跑过一个品牌；页面页头、页面数据的文件地址、打包脚本的默认输出名都写死了这份数据。
2. **真人复核之后，能不能马上得出结论？** 下载文件现在没人接：不能汇入样本库，也没有脚本能比较"规则、模型、规则加模型"三种做法谁更接近人。真人试用那天拿到的标注，只能手工去看。

## 2. 本轮目标

从"一份数据的演示"变成"可复用、可校准的研判工具"：

- **G1 复用**：换一个品牌车型，从取数到页面不改代码；页面能在两份数据之间切换。
- **G2 校准就绪**：真人复核一回来，当天就能跑出三种做法的对比和"模型这一步留、改、还是去掉"的依据。

**本轮不做**：企业数据；账号与多人协作；静态站部署（待用户决定，见第 8 节）；模糊匹配或实体消解引擎；任意问题的通用本体平台；页面英文版；调提示词（没有人工标注之前不改）。

## 3. 用户与场景

- **质量工程师**：打开页面，选数据集和召回，逐条复核范围外投诉，下载结果。
- **FDE / 用户本人**：拿第二份数据给潜在客户演示"换一家车企也能跑"；试用结束后把复核文件交给系统，拿到对比结论。

## 4. 需求

优先级：P0 本轮必须完成；P1 本轮做，可随 P0 之后；P2 有空再做。

### R1 数据集说明从数据里读（P0）

快照记录这份数据的范围：品牌、车型、年款区间、取数时间；页面页头、页面数据文件名、打包脚本的默认值都从这里来，不再写死"雪佛兰 Bolt"。

验收：
- `fetch_nhtsa_snapshot.py` 生成的快照带 `scope`（品牌、车型列表、年款区间）；现有 Bolt 快照补上这项，不重新取数。
- 复核页页头显示的数据说明来自页面数据；`git grep` 复核页和页面逻辑源码里不再出现 "Bolt" 字样。
- 打包脚本按快照生成输出文件名（如 `nhtsa-chevrolet-bolt-ev-bolt-euv-2017-2023.json`），不再用写死的默认名。
- 首页 `/landing` 的"验证"一段是对外宣传，保留 Bolt 的数字，不在本需求范围。

### R2 第二份数据跑通（P0）

测试数据：**现代 Kona Electric 2019–2021**。2026-09-13 实查：2019、2020 款各有 3 个召回，部件含电气系统与液压刹车，投诉分别 54、185 条。刹车召回与 Bolt 一样写作 "SERVICE BRAKES, HYDRAULIC"，正好检验名称对应在另一家车企上是否同样成立。

验收：
- 取数 → 在线运行 → 打包 → 页面，全程不改代码；如果必须改，交付一份改动清单，逐条写明改了什么、为什么是这份数据逼出来的。
- 记录本次运行的事实：本体提交次数与被退回的原因、模型提出与被拒的名称对应、每个召回的候选数与三类分布、未进入任何候选的投诉数。
- 与 Bolt 结果并排写一段对比：两份数据上相同与不同的地方。

### R3 页面切换数据集（P0）

页面数据目录下有一份数据集清单；复核页页头能切换数据集；每份数据的复核各自保存，互不干扰。

验收：
- 清单文件列出每份数据的名称、页面数据地址、召回数、投诉数、取数日期，由打包脚本生成或更新。
- 在 Bolt 与 Kona 之间切换：标签页、召回选择、复核标记都按数据集分开；刷新后回到上次选的数据集。
- 某份数据读不到或格式不对时，只提示这一份，其他数据照常能用。

### R4 复核回流为样本库（P0）

下载的复核文件可以交给脚本汇入仓库里的样本库，成为以后比较提示词和做法的固定样本。

验收：
- `scripts/import_reviews.py --input <下载文件> --reviewer <姓名或代号>` 把复核逐条写进 `examples/labels/<数据集>.jsonl`：投诉编号、所属召回系列、人工结论、备注、模型结论与提示词版本、复核人、复核时间、本体哈希。
- 本体哈希与当前页面数据不一致时拒绝导入并说明原因；同一复核人对同一条投诉重复导入时保留最新一次，并在输出里列出被覆盖的条目。
- 样本库文件入库前检查不含本机路径和密钥。

### R5 三种做法对比（P1）

在样本库上比较：只用规则、只用模型初判、先规则筛再看模型。规则写在代码里、作为基线，不调参。

验收：
- `scripts/compare_judgments.py --labels examples/labels/<数据集>.jsonl` 输出一张表：每种做法与人工一致的条数、判错的条目（分"该判是却判否"与"该判否却判是"），以及样本数；样本少于能下结论的量时如实写明，不给百分比外推。
- 规则定义与迭代 1 的对比实验一致：投诉标了起火，或原文出现 fire / smoke / burn / flame / thermal / melt。
- 离线测试用手工构造的样本文件验证计算正确；真实结论只在有真人标注后产生。

### R6 复核人留名（P1）

样本需要知道是谁标的。页面"结果"页可以填写复核人（本机保存），下载文件带上它；R4 导入时命令行参数优先。

验收：填写后刷新仍在；下载文件每行带复核人；不填也能下载，导入时必须补上。

### R7 小项（P2）

- 网站 favicon 与 GitHub 社交预览图，从像素 Logo 切。
- 清理 GitHub 上已合并的旧分支，只留 main、开发分支和归档标签。
- 更新"现状与路线"网页的截图为新版界面。

## 5. 非功能要求

- 不引入新依赖；每个模型调用带提示词版本、temperature 0；先写失败测试再实现，改已有测试单独提交。
- 数据来源可追：快照记录请求地址与取数时间，清洗规则和删除条数写进快照；本体、数据、页面用哈希锚定。
- 公开仓库：推送前查本机路径、个人信息、客户名与密钥。
- 页面在 1440 宽和 390 宽下都能用，没有横向溢出。

## 7. 风险

- **Kona 的投诉接口可能不完整**：Bolt 2017 款只返回 4 条投诉就是先例。R2 要记录每个年款的返回条数，异常的如实标注。
- **模型在新数据上搭出不同的本体**：这正是要检验的；只要通过核验就接受，差异写进对比。
- **一次试用的样本量小**：30 分钟大约几十条，只够看方向，不够给准确率。R5 的输出必须写清样本数。
- **用户找人的时间不确定**：M1、M2 不依赖它，先做完；M3 等人。

## 9. M1 结果（2026-09-13）

**R1 已完成**：快照带 `scope`（品牌、车型、年款区间）；数据集编号与名称由它生成；复核页页头、页面数据文件名、打包脚本都从数据读，复核页源码里不再出现 Bolt。

**R3 已完成**：`landing-page/public/data/index.json` 列出数据集，打包脚本发布时自动更新；页头下拉切换数据集，两份数据的确认状态、标签页、复核各自保存，刷新回到上次的数据集；某份数据读不到只提示这一份。`build_public_review_pack.py --check` 不带参数时核对清单里的全部数据集。

**R2 已完成，改动清单两条**，都是第二份数据逼出来的，改在 NHTSA 取数这一层，本体、范围、判断、打包、页面都没为 Kona 改：

1. NHTSA 查一个不存在的车型年款组合时回 400，内容是 0 条（投诉接口字段叫 `count`，召回接口叫 `Count`）。现代把 2021 款投诉里的车型名从 KONA ELECTRIC 改成了 KONA EV，召回接口却仍用 KONA ELECTRIC。改为：400 且 0 条时按"这个年款没有这个车型"记下，写进请求记录的 `note`；其他错误照旧报错。Kona 这次有 6 个请求属于这种情况。
2. NHTSA 投诉接口按车型名模糊匹配：查 "kona electric" 返回了 273 条燃油版 "KONA" 的投诉（其中 172 条提到汽油、燃油、机油或发动机；电动版 107 条里一条都没有）。改为：取数时去掉车型一个都不在所请求车型之内的投诉，规则和删除条数写进快照 `cleaning`。Bolt 按此规则删除 0 条。

Kona 在线运行（`examples/nhtsa/runs/2026-09-13-kona-deepseek-flash-v1.json`）：

- 本体第 2 次提交通过（第 1 次漏写 2 个字段的去向），召回、车型年款、部件、投诉四类核心对象与 Bolt 相同，另多了一类"车辆（车架号）"背景对象，这一轮 Bolt 的本体没有这一类（更正：原先写成"结构与 Bolt 相同"，2026-09-14 模拟试用时发现不对）；模型自己加了"产品类型 = Vehicle"的过滤条件；时间字段同样选了召回报告日期与投诉提交日期。
- 名称对应：模型同样只提出"SERVICE BRAKES → SERVICE BRAKES, HYDRAULIC"，多连上 11 条，0 条被拒。这条对应在两家车企上都成立。
- 4 个召回：电池管理软件 20V630000 与牵引电池 21V127000 都是"锂电池可能短路"、覆盖 2019–2020 款，各 69 条候选，范围内 59、所有召回之外 10，外面这 10 条都是 2021 款、都在召回之后；电控单元冷却液泄漏 22V941000 只覆盖 2021 款，范围内 10、之外 59；液压刹车 20V748000 11 条全在范围内。
- 107 条投诉里 28 条没进入任何召回的候选。

与 Bolt 的对比：

- 相同：四类核心对象、过滤与时间字段的选择、刹车名称对应，都在第二家车企上原样成立，代码核验同样退回一次后通过。Kona 多出的车辆背景对象是模型看了这份数据自己加的，代码没有为它改动。
- 不同：现代的三个电池召回把部件写到不同的细度（电池管理软件 / 牵引电池 / 热管理冷却液），原文也不互相引用，所以既不连成系列，也不算"其他同类召回已覆盖"。考虑过把"同类"放宽为"部件在同一条层级路径上"，推演后会让冷却液召回去覆盖短路投诉，更误导，所以保持"部件写法完全相同"才算同类；判断是不是同一缺陷仍交给原文判断和人工复核。
- Bolt 快照补 `scope` 后重跑（`2026-09-13-bolt-deepseek-flash-v5.json`）：电池召回范围外 43 条全部在召回之后、刹车名称对应多连上 34 条、13 个召回都有初判，与上一轮一致。

## 10. M2 结果（2026-09-14）

**R4 已完成**：`scripts/import_reviews.py --input <下载文件> [--reviewer <代号>]` 按下载文件里的数据集编号找到当前页面数据，逐条写进 `examples/labels/<数据集>.jsonl`。每行带投诉编号、召回系列及其成员、人工结论、备注、模型结论与模型名、提示词版本、复核人、复核时间、导入时间、本体哈希，以及规则要用的起火标记和投诉原文（公开数据）。拒绝导入的情况：本体哈希不一致、数据集不在清单里、投诉不是该系列的候选、结论无法识别、缺复核人、任何字段含本机路径或疑似密钥；拒绝时什么都不写。同一复核人、同一系列、同一条投诉再次导入时以最新一次为准，被覆盖的条目逐条列出。模型结论取自页面数据而不是下载文件，两者由本体哈希锚定。

**R5 已完成**：`scripts/compare_judgments.py --labels <样本库>` 输出全部样本和按召回系列分开的表：与人一致、该判是却判否、该判否却判是、没有结论（模型说不清或没有初判），并列出判错的投诉编号。"说不清"的人工结论不计入，只报条数；不换算比例。规则是迭代 1 的起火基线，按词首匹配（"misfire"不算），所以它只对起火类召回有意义，输出里写明了。"先规则再看模型"＝规则不命中即判否，命中后以模型结论为准。

- 同一条规则在当前 Bolt 运行（v5）的电池召回 20V701000 上筛出 87/287；路线文档里的 82/287 是更早一轮运行的数，不可直接比较。

**R6 已完成**：结果页"下载"卡片里填复核人，本机保存、所有数据集共用；下载文件在文件头和每一行都带复核人与数据集编号；不填也能下载，导入时必须用 `--reviewer` 补上，命令行优先。

验证：后端 131 项（新增 16 项，用手工构造的页面数据和下载文件）、前端 35 项、Sites 4 项全过。在真实 Bolt 页面数据上走通一遍：用页面的导出函数生成下载文件 → 导入 → 缺复核人被拒 → 补 `--reviewer` 重导并列出覆盖 → 对比出表；这里的人工标记是构造的，不是结论。浏览器里填复核人、刷新仍在、下载文件带复核人与数据集编号；390 宽没有横向溢出。

顺带修正：页面标题与描述还是旧定位（"AI FDE Decision Compiler"），已改为召回范围研判。

## 11. 模拟用户试用与修正（2026-09-14）

M3 之前先用三个模拟用户在本机页面上完整走了一遍：一位第一次试用的质量工程师（桌面、30 分钟）、FDE 演示并回流导入、一位质量部经理用手机看 5 分钟。每条问题都在主线程对照代码或数据核实后才采纳。

**最重要的发现**：首页大数字"43 条电池召回范围外投诉，全部发生在召回之后"容易被读成"漏召回 43 辆"，而模型对这 43 条的初判是 41 条不是、2 条说不清、没有一条是同一缺陷。首页改为写明这是待复核的候选，并附模型初判分布。

**"确认本体"重做为"口径核对"**：工程师和经理都说看不懂自己在确认什么，只因为那是唯一能点的按钮才点，等于盲确认。新页面问质量工程师答得出的问题，全部从数据生成：数据范围与取数时的清洗；召回和投诉靠什么对上；哪些投诉算候选（投诉部件等于召回部件或是它的上一层，附本数据里候选最多的例子）；召回前后按哪两个日期比较。每条名称对应要逐条判"对 / 不对 / 说不清"才能开始复核，判断可随时改、存在本机、随下载带走；判为不对或说不清时，经这条对应连上的投诉在复核页有提醒。对象类型、关系、未用字段和每次提交被退回的原因收进"技术细节"。

**修掉的问题**：

1. 刷新后回到原来的标签页、召回、分类和那一条投诉（此前只保留复核记录，人被送回召回列表）。
2. 键盘复核：投诉列表只让选中的一条进入 Tab 顺序，上下方向键切换，1、2、3 直接标"同一缺陷 / 不是 / 说不清"（此前要按 26 次 Tab 才到判定按钮）。
3. 导入脚本只列出结论或备注真的变了的条目，并报新增、改动、未变各几条；输出全中文（此前重导一批会把没变的也列成"被覆盖"，还夹着 same、different）。
4. 对比表在有多位复核人时，判错条目带复核人（此前同一编号出现两次看不出是谁）。
5. 找不到文件或文件不是 JSON 时，两个脚本都说人话（此前是 Python 原始报错）。
6. 首页"验证"一段改为两份数据，边界改为"只在两份公开数据上验证过"；顺带更正"模型两次被退回后通过"为"第 1 次被退回、第 2 次通过"（两份数据都是）。
7. 页面数据保留每次本体提交被退回的原因（此前只剩次数）。
8. 手机上的导航改为换行排列（此前横向滚动但看不出来，像被切掉）。

**其他**：复核人一栏里出现本机路径或像密钥的内容时，页面当场提示并禁止下载；不填复核人时提示导入时要补；手机上点列表有按下反馈；窄屏点开投诉后滚到详情改在渲染之后执行；首页装饰图 608KB → 54KB，浅色 Logo 260KB → 88KB；README 写明样本库默认写进公开仓库；前端测试命令去掉一个早已删除的测试文件。
