# 迭代 4 需求 · 2026-09-16

开发前讨论的产物，等 Eddie 拍板后再动手。讨论方式：四个视角的评审并行读代码（可移植的定义与发布契约、真实交付现场、减法与风险、怎么证明做成了），主线程逐条回到代码和数据里核实，分歧写在第 7 节。讨论材料在会话 scratchpad 的 `prd4/`。

## 1. 这一轮要解决什么

Eddie 给的小目标：用户确认过的对象定义、关系和查询口径，能不能成为下一次任务继续使用的基础。

现在离这个目标最近的两块是逐项确认（存成参考本体）和固定验收问题（存成题目加认可过的查询）。但它们现在经不起两件最普通的事：模型下次换个名字、客户给的是三张表而不是一张。这一轮就修这两件，并让走完一遍之后有东西能带去开会。

范围仍是本体建设，不碰运行：动作执行、能力开放这两层不做，权限、同步、图库、向量库都不做。

## 2. 必做

### F1 验收问题按语义对上，而不是按模型给的名字（M）

现在 `ontology_acceptance.check_acceptance` 直接拿存下来的查询去查新本体，而查询里写的是上一次模型起的 key。实测同一份文件多次运行，key 会变：示例公司的"售后工单"有一次叫 `service_ticket`；芝加哥合同里同一条供应商与合同的关系，四次分别叫 `vendor_contract`、`contract_awarded_to_vendor`、`vendor_wins_contract`、`vendor_undertakes_contract`。所以业务上什么都没变，重跑也会大量误判"查询失效"，这会直接毁掉验收问题的可信度。

做法：执行前先把存下来的查询映射到这一版本体，用 `ontology_compare.match_types` 那套"读同一张表、用同样的识别字段"的匹配（`prefill_from_reference` 已经在用），关系按两端匹配。映射不到才算断链，并且说清是哪个对象或哪条关系对不上。

验收：
- 把关系改名后重跑，验收问题仍能答出同样的数字。
- 把对象的 key 改名（标签和识别字段不变）后重跑，仍能答。
- 对象真的没了，状态是"查询失效"，原因里点名那个对象。
- 字段没了（已有测试）行为不变。

不做：模糊匹配名字、让模型去猜新旧对应关系。

### F2 一次上传多份表（M）

现在前端 `input` 没有 `multiple`，只取第一个文件；后端 `load_table_file(filename, data, purpose)` 也是单文件。客户给三五张分开导出的表时，跨表关系根本画不出来，顾问得自己先合并成一个工作簿。同一个工作簿里的多个 sheet 本来就会一起建模，但页面从没说过。

做法：前端允许多选和多文件拖放；后端把多份表合成一个来源包（每份表一个 source，重名的按文件名区分），其余流程不变。总大小沿用现有上限，超了在上传前就说明。

验收：
- 三份 CSV 一起传，得到一个本体，并且有跨表关系。
- 传一份的行为和现在完全一样（现有测试不变）。
- 其中一份读不了时，说清是哪一份，不要整批失败得不明不白。
- 页面在选好文件后列出这次要一起建模的表。

不做：跨次合并（这次传的和上次传的拼在一起）、文件夹上传、表和文档混传。

### F3 真实客户文件试跑一次（非功能，必做）

到今天为止，所有验证都来自合成数据、公开数据或模拟用户。结算线 11-29 要看的是真实使用。这一轮要求：Eddie 拿一份真实客户文件（自己脱敏）走完上传、确认、定验收问题、下载，全程不改代码，把卡住的地方记下来。

验收：`docs/PRD_ITERATION_4.md` 里追加一段试跑记录，写清用了什么文件、花了多久、哪一步卡住、产出敢不敢直接发给客户。

## 3. 应做（都小，且都是为了让试跑有东西可交）

### F4 一页能带走的纪要（S）

现在走完只能下载两份 JSON，关系图是内联 SVG 也导不出来，开会只能靠截图。加一个 Markdown 导出：这次用了哪些文件、有哪些对象和关系（人话）、数据体检要点、固定的验收问题和口径、确认人和时间。

验收：下载的 `.md` 在别的机器上打开可读，不依赖本工具，并且里面每个数字都能在页面上找到出处。

### F5 导出的定义包自解释（S）

下载的参考本体现在缺"为了回答什么问题"（`run.purpose` 已有，没放进去）和 schema 版本号，并且验收问题是另一份文件、互不引用。导出时补上这两个字段，并把已存的验收问题拼进同一份下载。

验收：下载的 JSON 里能看出它是为哪个建模目的、哪一版格式、配了哪几道验收问题；`parse_reference` 仍能读回它（现有对照功能不受影响）。

不做：在存储层把 `references/` 和 `acceptance/` 合并成一份文件（两次保存是独立动作，合并会引入写冲突）。

### F6 断链要看得见（S）

客户发来新版文件（哪怕只多一行），sha256 变了，上次的确认和验收问题就找不到了，而且页面什么都不说，看起来跟第一次上传一样。这一轮不做自动继承，只做可见：按文件名找到过同名的旧结果时，明确写出"这份文件和上次不是同一份，上次的确认没有自动带过来"。

验收：同名文件多一行后上传，页面出现这句提示；确实是第一次传的文件不出现。

不做：自动继承旧确认、内容相似度比较、跨版本记忆（等真的开始重复处理更新文件再说）。

### F7 存不住要说出来（S）

`saveLocal` 现在用 `try/catch` 把失败吞掉，结果太大存不进浏览器时用户不知道，刷新后结果凭空消失。改成提示"这次结果太大，没能存进浏览器，请下载保存"。同时给答案的字节数加一条断言，而不是只限制 200 组——分组名变长时 200 组也能重新涨回几 MB。

验收：模拟存储写入失败时页面出现提示；一条测试量 `json.dumps(answer)` 的字节数在几百 KB 以内。

## 3.5 开工前评审定下的设计（2026-09-16 八人面板，主线程逐条核实）

### F1 怎么做

- 重映射写在 `check_acceptance` 里：把存下来的查询改写成这一版本体的 key，再调现成的 `run_query`。不给 `run_query` 加映射参数，执行引擎保持单一职责。
- 必须多存一份快照。现在 `parse_acceptance` 只存题目、查询、口径、上次答案，而语义匹配靠"来自哪张表、按哪些字段识别"，查询里没有这些信息。保存验收问题时一并存下查询用到的对象和关系当时的样子；已经存下的旧题目没有快照，按现在的行为走（按 key 直查），不算回归。
- 关系匹配只看两端类型是不够的：同两端如果有两条含义不同的关系（订单与产品之间既有"包含"又有"退货"），现在的匹配会取第一个命中，可能悄悄配错，给出假的"一致"，这比误判失效更危险。规则定为：两端能对上且候选唯一才算映射成功；有多个候选就标"对不上，请人确认"，不猜。
- 字段不用额外处理：字段解析按路径匹配，对象改名不影响。

### F2 怎么做

- 请求契约只加不改：保留现在的单文件形状，新增可选的多文件形状。表格和文档不混传，混传直接拒绝。
- 一组文件的身份：每份文件各算 sha256，排序后拼接再算一次，作为这一组的 sha256。这样换个选择顺序重传仍能找到上次的确认和验收问题，服务端三处按 sha256 查找的代码不用改。
- 表名冲突要当心，它和 F1 耦合：不同文件里叫"客户""订单"的表很常见（实测两份示例文件就撞了）。规则定为：只有同一批次里真的撞名才加文件名后缀，不撞就保持原名；并且 F1 的匹配保留按名字兜底的第二条规则，避免表名一变就断链。
- 大小限制从单文件改成判一批的总字节，HTTP 请求体上限也要跟着调大，否则会先被通用的"请求太大"拦掉、看不到是哪一份超了。实测两份真实文件加起来 8.1 MB，已经逼近现在的 10 MB 上限。
- 一份读不了就整批失败，并点名是哪一份。不做"跳过继续"：丢掉的那张表可能正是连接两端的那张。
- 前端：允许多选和多文件拖放，文件卡片改成列表，显示总大小和这次会一起建模的文件。

### F4、F5、F6、F7 的口径

- 纪要（F4）只用已有字段在前端拼出来，不新开后端接口。不进纪要的内容：模型的原话和理由、没有人确认过的判断（没确认时要写明"这是模型草稿，未经确认"）。
- 导出自解释（F5）在下载的参考本体顶层加建模目的、导出格式版本，并把验收问题拼进来。已验证参考本体的读取器会忽略多余的键，现有对照功能不受影响。
- 断链提示（F6）改口径：不按文件名判断（客户发新版常常改名，那样这条提示可能永远不出现），改成这次上传没有已存的确认或验收问题时就说明白，并说清系统是按文件内容认人的。
- 存不住要说出来（F7）：`saveLocal` 现在把失败吞掉，要改成可以注入存储以便测试，并在页面上提示。

### 现场动线上的文案（顺手改，不单列需求）

- 进度里"正在等另外两次建模"这类内部机制的说法，换成客户听得懂的话。
- 图上每个对象并排显示模型内部的英文 key 和中文名，当着客户面容易被问"这是什么"，图例里要有一句解释。
- 等待时间实测 8 到 10 分钟，这一轮没有任何需求能缩短它。缓解办法是零成本的：把上传放在寒暄之前。

## 4. 这一轮不做

跨版本确认记忆的自动继承、一段制度核对一张表、关系基数与字段类型导出、文档多次建模投票、动作执行与写回、权限与多人、部署上云、图数据库、向量库、多 Agent 编排。进入条件见 `DEVELOPMENT_GUARDRAILS.md` 的"等触发再做的方向"。

## 5. 顺序与预算

一到两天：F1 → F2 → F4/F5/F6/F7 → F3 试跑。F1 是修今天刚做的东西里的缺陷，排第一；F2 是唯一的新功能；F4 到 F7 都是半天以内的小改，合起来让试跑有产出、有诚实的边界说明。

## 6. 验证方式

每条需求先写失败测试再实现。除此之外，这一轮固定五条人工检查，每次真实数据跑完都过一遍（自动化测试查不出来的那类错误）：

1. 打开浏览器控制台，看有没有被吞掉的报错。
2. 刷新页面后，上次的结果和确认还在不在。
3. 随机挑三到五个问答分组的数字，回原始文件手数一遍。
4. 同一份文件重传一次，验收问题是不是给出"和上次一致或不一致"的结论，而不是又起了一套。
5. 换一份内容近似但不是同一份的文件，确认"上次的确认没带过来"这件事在页面上看得见。

## 7. 讨论里的分歧和取舍

- 减法视角主张这一轮只做一条新需求，其余时间全给真实试跑。我保留了 F2 这一条新功能，因为真实交付现场的第一步就卡在只能传一份文件上；F4 到 F7 都不是新能力，是把已有产出变成能带走、能说清边界的东西。
- 可移植定义视角提议把确认和验收问题合成一个定义包。只在导出时拼接，不动存储，理由写在 F5。
- 真实现场视角认为三次建模稳定性、多维分组、占比这些在首访半天里用不上。这一轮不删也不扩，先看真实试跑里顾问会不会用到。
- 验证视角提出的"测试夹具太小，真实体量的问题只有跑真数据才会暴露"，这一轮用 F7 的字节数断言和第 6 节的人工检查来兜，不新增测试框架。

## 8. 八人面板补充的几条判断

- 多表建模的风险被我高估了：示例公司那份四张表的文件在本机跑过 17 次，全部通过核验，平均两次提交，关系数稳定在 3 到 4 条。多文件上传走的是同一条代码路径，不必为"跨表关系建不出来"另做准备。
- 红队认为最可能白做的是断链提示，理由是触发条件（同名文件）可能从不出现。已按上面的新口径改掉，不再依赖文件名。
- 试跑的脱敏要点：出本机的不只是每列最多三个示例值，取值不超过 12 种的列会把全部取值发给模型（用于出题），文档则是整篇按块发送。识别字段如果要哈希，必须同一个值哈希后仍相同，否则跨表关系直接建不出来。文件名会原样进结果和导出，客户真名要先改。
- 上传接口如果做成破坏性改造而不是新增可选形状，会打碎一整批现有测试。遇到这种情况应该停下来问，而不是改测试。
