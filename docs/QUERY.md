# 本体查询（OntoPoc Query）

会一点 SQL 就能写，写的是业务对象，不是表。每个结果都说明它用了哪些确认过的定义；每次查询都按提问人的权限算。

```sql
SELECT c.客户名称, sum(o.金额) AS 合计
FROM (o:订单)-[:订单属于客户]->(c:客户)
WHERE o.状态码 <> '已取消'
GROUP BY c.客户名称
ORDER BY 合计 DESC
LIMIT 3
```

## 为什么不直接写 SQL

如果只有一个业务库，用一个通用智能体加数据库连接不就够了？下面是同一批问题、同一份演示数据，一边是有库权限的人手写的 SQL，一边是本体查询。数字来自 `scripts/query_value_report.py`，不用模型，可以重跑。

**平常的问题，两边数字一样。** 5 道题（计数、带条件求和、前三名、按客户等级分组、售后工单经过订单到产品品类的两步路径）结果完全相同。本体查询不是一种新的出错方式。

**五个陷阱。SQL 都给了一个数字，没有任何提醒：**

| 情况 | 手写 SQL | 本体查询 |
|---|---|---|
| 行规则：Vera 只能看客户 KH001 的订单 | `count(*)` = **160**，谁来问都一样 | **5**，并说明“按行规则只读了你的行（客户编号 = KH001）” |
| 代码换了含义：新上传的订单表里状态码整体加 1 | `状态码 = '2'` = **48**，数的其实是生产中的订单 | 拒绝，并指出“状态码”的取值变了：新出现 3，不再出现 0，要谁再确认 |
| 连接把行算两遍：客户表里 KH012 有两行 | `JOIN` 后合计 **2,737,200**，真实订单总额是 2,726,470 | 拒绝，并说明 KH012 重复 2 次，连上的 2 行会多出 2 行，按客户汇总会重复算 |
| 隐藏的列：金额只给 Ann 看，Carl 来问 | `sum(金额)` 照样读出来 | 对 Carl 来说没有这个属性，回答和写错属性名一样，不透露它存在 |
| 列存成文字（DIP 的数据集除主键外都是 text）：金额超过 20000 的订单 | `金额 > 20000` = **160**，因为文字永远“大于”数字 | **57**，按数字比。读不成数字的值会单独数出来，不会悄悄算进去或丢掉 |

把 JSON 换成本体查询，写同样 5 道题要写的字从 902 个降到 423 个，和 SQL（424 个）差不多。模型写它是不是更少出错，还要用真实模型测（第 4 步），现在不下结论。

## 怎么写

- `FROM` 写路径：`(o:订单)-[:订单属于客户]->(c:客户)`。箭头可以反过来写 `<-[:关系]-`，不确定方向就写 `-[:关系]-`。几条路径用逗号隔开，同一个简称表示同一个对象：`(o:订单)-[:订单属于客户]->(c:客户), (o)-[:订单买的产品]->(p:产品)`。
- 对象类型和关系可以写中文名，也可以写英文名（`order`、`order_customer`）。
- `SELECT` 里只算一个数：`count(o)`、`count(*)`、`sum(o.金额)`、`avg(o.金额)`、`share(o.状态码 = '已取消')`（占比）。其余的列要写进 `GROUP BY`，和 SQL 一样。
- `WHERE` 写在被数或被算的对象上，可以用 `=`、`<>`、`NOT IN (…)`，多个条件用 `AND` 连起来。代码列直接写含义，例如 `'已取消'`，查询会换成它的代码，并在结果里注明用了这个含义。
- 范围：`o.金额 > 20000`、`>=`、`<`、`<=`、`o.下单日期 BETWEEN '2026-01-01' AND '2026-03-31'`（两头都算）。
  - 两边都能读成数字就按数字比，都能读成日期就按日期比。
  - 日期认 `2026-01-02`、`2026/1/2`、`2026.01.02`、`2026年1月2日`，带不带时间都行，按那一天算。一个日期里只能用一种分隔符，`2026.5` 和 `2026-01/02` 都不算日期。日期要加引号。
  - 只写月份（`'2026-02'`、`'2026年2月'`）表示整个月：`<= '2026-01'` 包括 1 月整月，`> '2026-02'` 从 3 月算起，`BETWEEN '2026-01' AND '2026-02'` 是 1、2 两个月。
  - 下限比上限大（例如 `BETWEEN 9 AND 1`）会直接拒绝，不会悄悄返回 0。
  - 边界既不是数字也不是日期时，直接拒绝。数据里读不成数字或日期的值不算符合，并在结果里单独数出来，附上几个例子。
- 按月、按年：`SELECT month(o.下单日期), sum(o.金额) … GROUP BY month(o.下单日期)`，`year()` 同理。没有日期或读不成日期的对象算在“没有可分的值”里。
- `ORDER BY` 按算出来的那个数排（`DESC` 从高到低，`ASC` 从低到高），`LIMIT n` 只留前 n 组。
- `$名字` 是参数，调用时用 `params` 传值。参数只能当值用，不会被当成查询文字：在看板上输入 `KH001' OR '1'='1`，查的就是编号为这串字的客户，结果是没有数据；把值直接拼进 SQL 字符串的模板会因此数出全部 160 张订单。
- `SELECT count(c) FROM (o:订单)-[:订单属于客户]->(c:客户) WHERE o.状态码 = '已取消'` 数的是有已取消订单的客户。

## 画成图：SELECT GRAPH（第 5 步）

不算数，而是把对象本身和它们之间的关系画出来：

```sql
SELECT GRAPH
FROM (o:订单)-[:订单属于客户]->(c:客户)
WHERE o.状态码 = '已取消'
LIMIT 10
```

- FROM 里的第一个节点是起点。`WHERE` 只能写在起点上，和算数时一样。满足条件的起点对象按数据里的顺序取前 `LIMIT` 个，不写就是 20 个，最多 100 个。
- 每条路径从这些起点走出去，走到的对象和连线都画出来。一张图最多 400 个对象，超过了就停下，并注明“只画了一部分”。
- 回答里写着一共有多少个起点对象满足条件，画了其中几个。
- 按提问人能读的行和属性画：有行规则就只画他的行；藏起来的列不出现在节点上，比如客户名称对他藏起来，客户节点只显示编号。
- 用到的含义和关系都要是确认过的，和算数一样。订单里写的客户编号在客户表里找不到时，这张订单连不到客户。
- 浏览者只能看数，看不到一个个对象，所以对浏览者拒绝（403）。看板组件和问答模型也只用算数的查询，`SELECT GRAPH` 只在问答页的“写查询”里用。
- 在页面上，起点在左边一列，往右每一列多走一步。点一个对象，和它相连的线会亮起来。

## 现在不支持的写法

下面这些写法会直接拒绝，并说明原因，不会被理解成别的意思：

- `OR`、`IN` 多个值、`LIKE`、`IS NULL`、`HAVING`、`JOIN`；
- 按周、按季度分组（现在只有 `month()` 和 `year()`）；
- 条件写在另一个对象上（例如按客户等级筛订单）；
- 一次算两个数；
- `FROM` 里写了但没用到的节点。SQL 多连一张表会悄悄去掉连不上的行，这里不会，所以要求删掉它。

## 语法（和 OntoPoc 无关的部分）

`src/ontology_poc_generator/ontopoc_query.py` 只依赖 Python 标准库。它的输入是一份目录（类型 → 属性，关系 → 两端），输出是一个结构化查询。有测试保证它不引用 OntoPoc 的其他模块，以后要单独拿出去，复制这一个文件就够了。

```
query     := SELECT item {, item} FROM chain {, chain} [WHERE cond {AND cond}] [GROUP BY group {, group}] [ORDER BY target [ASC|DESC]] [LIMIT n]
           | SELECT GRAPH FROM chain {, chain} [WHERE cond {AND cond}] [LIMIT n]
item      := group | agg [AS name]
group     := ref | month(ref) | year(ref)
agg       := count(var) | count(*) | sum(ref) | avg(ref) | share(ref = value)
chain     := node {edge node}
node      := (var[:type])
edge      := -[:relation]-> | <-[:relation]- | -[:relation]-
cond      := ref = value | ref <> value | ref != value | ref [NOT] IN (value {, value})
           | ref (> | >= | < | <=) value | ref BETWEEN value AND value
ref       := var.property
value     := 'text' | number | $param
target    := name | agg
```

名字可以是中文，也可以用反引号括起来。关键字不分大小写，`--` 后面是注释。

## 接口

- `POST /api/workspace/query {text, params?}`：按提问人的权限运行，返回 `status`、`answer`、`definitions`（用到的确认定义，带确认人）、`limited_by_rule`、`query`（编译后的结构化查询）和 `text`（规范写法）。写错时返回 400，并说明能写什么，例如这个类型有哪些关系、有哪些属性。
- `POST /api/workspace/query/text {query}`：把结构化查询（问答里模型写的那种）写回成本体查询文字。
- 浏览者和只读令牌都可以用，不调用模型，也不记入问答历史。
- MCP：外部智能体用 `ontopoc_query` 工具，见 [MCP.md](MCP.md)。
- 问答的每个回答都带着 `query_text`，也就是这道题写成本体查询的样子。代码列写的是确认过的含义（`'已取消'`），不是代码本身。只有这段文字能跑出同一个查询时才会带上。

## 在页面上

问答页有“提问 / 写查询”两种方式。“写查询”按你能看的行算，结果用和回答一样的卡片显示，包括用到的定义、谁确认的、行规则限制了哪些行。每个回答下面有“写成查询”和“改成查询”：点“改成查询”会把这道题的查询放进查询框，改完可以接着跑。

## 在看板上

看板的组件可以是一条本体查询（种类选“本体查询”），也就是一条存下来的查询。每次有人打开看板，都按这个人能看的行和属性重新算，不调用模型。

- **参数。** 看板可以有最多 4 个参数（名字、显示的名字、默认值），看板上方给每个参数一个输入框。查询里的 `$名字` 都要是看板的参数，而且都要有默认值，所以看板打开时总有数可看，保存时也能先算一遍、检查查询写得对不对。看的人在输入框里换一个值，按回车或离开输入框，所有用到它的查询都用这个值重算；清空就回到默认值。
- **每个人看到自己的行。** 同一个看板、同一个参数，只能看 KH026 的 Vera 看到的是她的 9 张订单，卡片下写着“只算了你看得到的行”；她把参数改成 KH001，看到的是“没有数据”，不是别人的数。用一个共享数据库连接的 SQL 看板，谁打开都看到同一个数。
- **看不到的不说。** 看的人算不了某个查询组件时，只说是哪一类原因：他看不到用到的类型或属性；用到的定义现在不是已确认的状态；或他填的参数值在这里用不了（同一个组件用默认值能算）。不说查询读了什么，也不给他看查询文字，因为原因里可能有对他隐藏的列名。具体原因只告诉看板的主人和管理员。查询组件不存“上次确认的数”。
- 筛选条（选字段的值）只作用于其他种类的组件；查询组件的条件写在查询里，用参数改。
- 接口：`POST /api/workspace/dashboards/data {id, bar, params}`，返回的 `params` 是每个参数和这次用的值；查询组件的结果和问答的回答同一个样子（`status`、`answer`、`text`、`definitions`、`limited_by_rule`），另带 `standing`。

问答页的“写查询”也认参数：查询里写了 `$名字`，查询框下面就出现对应的输入框。

## 让问答模型直接写查询（第 4 步）

`POST /api/workspace/ask {question, writes: "query"}` 让模型写本体查询，不写 JSON。默认还是 `"json"`。

- 模型看到的东西和写 JSON 时一样：类型、属性、关系、确认过的含义，以及问题里说出名字的视图，不看数据行。
- 它写的文字和“写查询”一样编译、运行，按提问人的权限算。用了哪些含义从文字里读（`=` 是要这些行，`<>`、`NOT IN` 是排除），不靠模型自己说。问题里提到了某个含义、查询里却没写，会拒答，不会给出一个错的数。
- 问题说出一个确认过的视图的名字（例如“有效订单”）时，代码先按这个视图取行再算；模型在 `views` 里写的、问题没说名字的视图不算，列在 `not_applied` 里。没说视图名字时，`beside` 里是这个类型上每个确认过的视图各自的数。
- 模型写的“等于”“不是”条件，问题里没说它的值（或代码列的确认含义的名字）就不算进去，也列在 `not_applied` 里；数值和日期范围照模型写的算。
- 文字编译不过，回答是“问法不支持”，写明哪里读不了，`written` 里留着模型写的原文。不重试，不出数。
- 回答多带 `writes: "query"` 和 `written`；`query_text` 是规范写法。
- 两种写法哪个更少出错，用 `scripts/real_model_check.py --writes both --repeat 3` 量：同一批问题，两种写法轮流问，各自计数。

## 和别的做法比

- **Cypher / ISO GQL / SQL:2023 的 `GRAPH_TABLE … MATCH`**：路径写法 `(a:类型)-[:关系]->(b)` 就是从这里来的，不是自己发明的语法。
- **Ontop（虚拟知识图谱）**：不复制数据，把对本体的查询改写成原库的 SQL。我们也不复制数据：查询编译成问答用的同一个查询，在提问人能读的行上算。数据量大了以后，可以照 Ontop 的思路把这一步下推到原库。
- **Malloy、LookML、dbt MetricFlow、Cube 这类语义层**：它们最有用的是关系只定义一次，并且连接时不重复算。我们的关系也只定义一次，而且数据会让行变多时，关系确认不了，查询会说出原因。
- **DIP**：数据先复制到平台的 Doris，智能体每次从数据分布里猜状态码的意思。我们的代码含义只确认一次，所有查询共用；数据变了就拒答，不会接着猜。
