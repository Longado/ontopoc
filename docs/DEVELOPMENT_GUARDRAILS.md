# OntoPoc 开发护栏

这不是架构文档，是决定"现在该不该做"的入口。

> 每次开发只允许把一个真实痛点推进到一个用户可完成的决策。不能改变用户下一步行动的代码，默认不做。

## 1. 现在的产品切片

2026-09-14 起：一个用户是 FDE / 实施顾问（或企业数据负责人）。一个问题：给一份公司的业务文件，能不能快速得到这家公司的本体，以及这个本体好不好。计划见 `PRD_ITERATION_3.md`。

```text
上传业务文件（数据表：CSV / Excel；文档：Markdown / 文本 / Word / PDF）
        ↓
模型提出本体（表格：只看表头和示例值；文档：每项引用原文）→ 代码核验，出错退回重做
        ↓
自动评测：本体和数据对不对得上（代码）/ 能不能回答业务问题（模型出题，代码执行）/ 与标准答案比对（代码）
        ↓
人看结果决定能不能拿去用；企业文件和结果只留在本机
```

召回范围研判（NHTSA）留作内置示例场景，不再往里加功能。

职责分工不变：数据来自来源，不由前端猜；模型只做判断，循环、重试、停止、核验全在代码；页面不重算一遍业务逻辑；人做最后决定；只有真实外部回执才算动作完成。

## 2. 开发前写清五行

```text
Pain：用户此刻卡在哪里？
Decision：用户需要做什么决定？
Outcome：这轮结束后，用户能完成什么新动作？
Non-goals：这轮明确不做什么？
Smallest path：复用哪些现有页面和函数完成它？
```

写不出一句话的 `Decision`，停下来先回到场景。

## 3. 新机制的进入条件

| 候选机制 | 只有出现这个阻塞时才加 |
|---|---|
| 新抽象或适配器 | 本轮已有第二个真实调用方，重复代码正在阻塞交付 |
| 持久化、多人协作 | 用户确实需要离开页面后继续、追责或分工 |
| 模糊匹配、实体消解引擎 | 名称对应（模型提出、代码核验）已证明不够用，且有标注数据说明差在哪 |
| 通用角色、任意问题的本体平台 | 2026-09-14 用户定向后，"任意公司文件生成本体"是主线；但仍不做编辑器、多人协作和"平台"式配置 |
| 新页面或新路由 | 现有页面无法承载用户完成该决策 |
| 部署、云服务 | 有人要在本机之外打开它 |

"以后可能需要""架构更完整""已有开源方案"都不是进入条件。

## 4. 模型调用的规矩

- 提示词是代码：放在模块常量里，带版本号，每次输出都记录模型名和提示词版本。
- 输出必须是结构化的，代码逐字段校验；判断必须附证据，代码核对证据真在原文里。
- 一次用户动作最多串 3 次模型调用；重试只在代码里，没有进展就停。
- temperature 固定为 0；换模型或改提示词前，先在人工标注的样本上比对。
- 一条规则或一个查询能做的事，不交给模型。

## 5. 何时停止扩张

- 新增的层、接口或状态不改变本轮用户决策；
- 前后端出现两套业务判断或两份权威状态；
- 为没有第二个调用方的未来需求设计通用能力；
- 测试主要保护内部结构，却没有保护用户可见结果；
- 功能名称从具体业务动作变成"平台、引擎、中心、框架"；
- 本轮文件范围超出开发前写下的 `Smallest path`。

## 6. 本轮完成定义

- 用户可见结果能支持目标决策；
- 数据缺口和能力边界直接显示给用户；
- 没有重复计算、重复权威源或未经需要的新基础设施；
- 只运行能证明这条用户路径成立的最窄检查，并报告确切结果；
- 未完成的真实数据、业务动作和客户效果仍明确保持未完成。

## 等触发再做的方向（2026-09-16 定）

极客夜话第 39 期之后列了几个方向，都要等条件出现再动，不要因为想到了就开分支：

- 跨版本确认记忆（客户发来新版文件）：等同一位顾问真的开始重复处理同一业务的更新文件。
- 一段制度核对一张业务表：等用户手里同时有制度和表，并且明确卡在两者怎么对应。
- 关系基数、字段类型导出：等有一个具体的接收方和导入约定。
- 文档也做多次建模投票：成本是每次上传三倍调用、长文档十来分钟，要先有人说长文档的结果他要用。

已经做了的"固定验收问题"是上面这些的共同判断标准：先用它看本体够不够用，再谈要不要记忆和制度。
