# OntoPoc 最小产品开发护栏

这不是新的架构层，而是决定“现在该不该做”的开发入口。

> 每次开发只允许把一个真实痛点推进到一个用户可完成的决策。不能改变用户下一步行动的代码，默认不做。

## 1. 最小产品架构

```text
业务触发与已有事实
        ↓
必要的确定性判断
        ↓
现有页面上的一个可见结果
        ↓
人工选择：纳入 / 排除 / 待补证
        ↓
会话内结果；不冒充真实业务执行
```

只有五个职责：

1. 业务系统或演示数据提供事实，不由前端猜测事实；
2. 一个领域函数产生本轮需要的判断，不建设通用规则平台；
3. 现有页面展示结果，不复制第二套计算逻辑；
4. 人负责最终选择，系统不自动确认根因或执行控制；
5. 只有真实外部回执才能说明动作已经完成。

## 2. 开发前必须写清楚

任何功能在动代码前，只回答下面五行：

```text
Pain：用户此刻卡在哪里？
Decision：用户需要做什么决定？
Outcome：这轮结束后，用户能完成什么新动作？
Non-goals：这轮明确不做什么？
Smallest path：复用哪些现有页面和函数完成它？
```

如果无法用一句话写清 `Decision`，停止开发，先回到场景讨论。

## 3. 新机制的进入条件

| 候选机制 | 只有出现这个当前阻塞时才允许加入 |
|---|---|
| 新抽象或适配器 | 本轮已有第二个真实调用方，而且重复代码正在阻塞交付 |
| 持久化 | 用户确实需要离开页面后继续、恢复或追责 |
| 工作流引擎 | 已出现跨天等待、失败重试或外部回执协调 |
| 数据连接器 | 已取得真实数据授权，并明确了只读范围与字段映射 |
| 多 Agent 编排 | 存在可独立验收的并行工作，且单 Agent 已成为实际瓶颈 |
| Hash、Receipt 或新契约 | 当前验收明确需要防篡改、重放或跨系统交接 |
| 新页面或新路由 | 现有页面无法承载用户完成该决策 |

“以后可能需要”“架构更完整”“已有开源方案”都不是进入条件。

## 4. 当前质量追溯 Demo 的产品切片

当前只服务一个痛点：质量异常发生后，业务人员需要跨 QMS、MES、WMS、PLM 手工追查，无法快速决定临时控制范围。

本切片的唯一主决策：

> 哪些库存、在制、待发运、在途或客户侧对象应进入临时控制或复检队列？

本切片只需要：

- 一个质量事件；
- 与事件有关的批次、BOM、版本、库存和发运事实；
- 四类结果：确定影响、可能影响、已排除、无法评估；
- 每个结果的依据或数据缺口；
- 人工选择“纳入、排除、待补证”。

本切片不需要：

- 自动确认根因；
- 真实冻结库存、停产或拦截发运；
- DemoBundle 平台、通用 Agent 框架或任务中心；
- EIP、Temporal、BaSyx、图数据库或新的外部服务；
- 为未来场景预留插件、仓储层或通用协议。

完成标准不是测试数量，而是业务人员能在同一个页面回答：

1. 当前要控制哪些对象？
2. 为什么？
3. 哪些对象已经排除？
4. 哪些对象因为缺数据还不能判断？

## 5. 当前开发顺序

1. 在现有质量事件页面展示四类受影响对象及依据；
2. 允许人工做“纳入 / 排除 / 待补证”的会话内选择；
3. 用一次业务走查判断这是否缩短了临时控制范围确认过程；
4. 只有走查暴露出明确阻塞，才决定是否增加保存、任务或真实数据接入。

候选原因排序可以作为辅助信息，但不能取代受影响对象范围这一主结果。

## 6. 何时停止扩张

出现任一情况，立即缩小计划：

- 新增的层、接口或状态不改变本轮用户决策；
- 前后端开始维护两套业务判断或两份权威状态；
- 为没有第二个调用方的未来需求设计通用能力；
- 测试主要保护内部结构，却没有保护用户可见结果；
- 功能名称从具体业务动作变成“平台、引擎、中心、框架”；
- 本轮文件范围超出开发前写下的 `Smallest path`。

## 7. 本轮完成定义

- 用户可见结果能够支持目标决策；
- 数据缺口和能力边界直接显示给用户；
- 没有重复计算、重复权威源或未经需要的新基础设施；
- 只运行能证明这条用户路径成立的最窄检查；
- 未完成的真实数据、业务动作和客户效果仍明确保持未完成。
