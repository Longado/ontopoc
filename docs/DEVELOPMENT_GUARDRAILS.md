# OntoPoc 开发护栏

这不是架构文档，是决定"现在该不该做"的入口。

> 每次开发只允许把一个真实痛点推进到一个用户可完成的决策。不能改变用户下一步行动的代码，默认不做。

## 1. 现在的产品切片

一个用户：质量工程师。一个问题：召回发布后，哪些同类投诉落在范围之外、需要复核或上报。

```text
公开数据快照（召回 + 投诉）
        ↓
模型提出本体 → 代码核验 → 名称对应（模型提出、代码核验）
        ↓
每个召回：覆盖范围、同部件投诉三类、召回前后
        ↓
模型初判（引用原文，代码核对）
        ↓
人工逐条复核；复核 = 标注；本机记录，不冒充业务处置
```

职责分工不变：数据来自来源，不由前端猜；模型只做判断，循环、重试、停止、核验全在代码；页面不重算一遍业务逻辑；人做最后决定；只有真实外部回执才算动作完成。

## 2. 开发前写清五行

```text
Pain：用户此刻卡在哪里？
Decision：用户需要做什么决定？
Outcome：这轮结束后，用户能完成什么新动作？
Non-goals：这轮明确不做什么？
Smallest path：复用哪些现有页面和函数完成它？
```

写不出一句话的 `Decision`，停下来先回到场景。

## 3. 新机制的进入条件

| 候选机制 | 只有出现这个阻塞时才加 |
|---|---|
| 新抽象或适配器 | 本轮已有第二个真实调用方，重复代码正在阻塞交付 |
| 持久化、多人协作 | 用户确实需要离开页面后继续、追责或分工 |
| 模糊匹配、实体消解引擎 | 名称对应（模型提出、代码核验）已证明不够用，且有标注数据说明差在哪 |
| 通用角色、任意问题的本体平台 | 第二份来源不同的数据跑不通，且放开角色是唯一办法 |
| 新页面或新路由 | 现有页面无法承载用户完成该决策 |
| 部署、云服务 | 有人要在本机之外打开它 |

"以后可能需要""架构更完整""已有开源方案"都不是进入条件。

## 4. 模型调用的规矩

- 提示词是代码：放在模块常量里，带版本号，每次输出都记录模型名和提示词版本。
- 输出必须是结构化的，代码逐字段校验；判断必须附证据，代码核对证据真在原文里。
- 一次用户动作最多串 3 次模型调用；重试只在代码里，没有进展就停。
- temperature 固定为 0；换模型或改提示词前，先在人工标注的样本上比对。
- 一条规则或一个查询能做的事，不交给模型。

## 5. 何时停止扩张

- 新增的层、接口或状态不改变本轮用户决策；
- 前后端出现两套业务判断或两份权威状态；
- 为没有第二个调用方的未来需求设计通用能力；
- 测试主要保护内部结构，却没有保护用户可见结果；
- 功能名称从具体业务动作变成"平台、引擎、中心、框架"；
- 本轮文件范围超出开发前写下的 `Smallest path`。

## 6. 本轮完成定义

- 用户可见结果能支持目标决策；
- 数据缺口和能力边界直接显示给用户；
- 没有重复计算、重复权威源或未经需要的新基础设施；
- 只运行能证明这条用户路径成立的最窄检查，并报告确切结果；
- 未完成的真实数据、业务动作和客户效果仍明确保持未完成。
