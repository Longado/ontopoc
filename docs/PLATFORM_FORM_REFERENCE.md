# 数据平台对象表单对照

OntoPoc 的产出最终要交给数据平台，由人在平台里把对象和属性一条条配出来。这份文档记录这类平台建对象时通常要填的表单，以及 OntoPoc 的产出怎么对应。只记表单的形状；各平台的批量导入契约（文件格式、主键规则、关系怎么表达）因平台而异，导入前必须实测。

## 1. 建一个对象要填什么

每个对象一张表单：对象的中文名称、英文名称，然后逐个属性填：

| 主键 | 展示 | 中文名称 | 英文名称 | 描述 | 类型 | 长度 | 属性类型 |
|---|---|---|---|---|---|---|---|

常见的约束：

- 每张表只有一个主键。
- 属性英文名要和导入文件的表头完全一致。
- 类型从一组固定取值里选（如 VARCHAR / INT / DOUBLE / DATE / DATETIME / TEXT / BOOLEAN），并填长度。
- 主数据对象（客户、产品）通常用名称做展示字段，交易类对象（订单、合同）用编号。
- 属性类型区分主键、外键、数据导入、系统生成、计算字段、枚举值。

关系一般不当普通对象建，而是单独配置：两端对象、关系类型、一对一 / 一对多 / 多对多。

## 2. OntoPoc 的产出怎么对应

| 表单要的 | OntoPoc | 来源 |
|---|---|---|
| 对象的中文名称、英文名称 | 对象的 label 与 key | 模型提出，人确认或改名 |
| 属性英文名 | 原表头 | 数据 |
| 属性中文名称、描述、展示字段 | 对象属性页里可编辑，可由字段释义员一次起草 | 模型起草，人修改 |
| 主键 | 识别字段 | 模型提出，代码核验 |
| 类型、长度 | 代码读每一个值得出 | 数据 |
| 属性类型 | 识别字段记"主键"，其余记"数据导入" | 代码 |
| 关系基数 | 代码数每条关系两端各挂几个 | 数据 |

导出（页面右上角"⤓ 表单"，或 MCP 工具 `export_forms`）按上面的列每个对象一张 CSV，附一份导入前说明。关系表不导出，等导入契约实测后再做。

## 3. 三处容易对不上

1. **多字段主键。** 一些对象本来就要靠两个字段一起识别，比如 CMS 医院数据里"医院编号 + 指标编号"确定一条指标结果、Northwind 的订单明细靠"订单号 + 产品号"。建模本身没错，但只收单主键的平台填不进去；页面和导出说明都会点出，导入前要合成一个字段或改建模。
2. **占位写法。** 缺失值写成 `\N`、`Not Available` 这类文字时，代码按文本判类型。这在技术上成立，但人会以为是整数列；要不要识别这类占位写法，得先定一条不靠猜的规矩。
3. **同一识别字段出现在多张表。** 表单一个字段一行，OntoPoc 按字段名合并，并写明来自哪几张表。

## 4. 不照搬的

数据平台是运行平台，OntoPoc 是建模之前的一道工序。平台上的这些能力不在 OntoPoc 的范围里：智能体编排与动作执行、权限、持久化的实例库、计算字段、多模态与向量检索、按业务环节给本体分组。

## 5. 界面上借了什么

工作台的组织方式参考了这类平台的常见布局：左栏按模块（数据接入、本体管理、本体关系、智能问答、数据体检），一次运行相当于一个工作空间、在左下角切换；本体管理里每个对象一张卡片，点进去是对象自己的页面（概览、属性、数据、确认）。
