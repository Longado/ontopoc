# OntoPoc 是什么 · 产品定义与边界

这份文档写不常变的东西：产品是什么、站在哪一层、产出什么、一份定义怎么走完一生。现状看 `FEATURES_2026-09-16.md`，开发红线看 `DEVELOPMENT_GUARDRAILS.md`，这一轮做什么看 `PRD_ITERATION_4.md`。定位改了就改这份，不要在新文档里重新写一遍。

## 1. 产品是什么

给实施顾问和本体团队用的本体起草与体检工具。上传客户的一份业务表或文档，几分钟内得到本体草案，以及它哪里有证据、哪里靠不住；人逐项确认后，这份判断存下来，下一次同一份文件自动拿它对照。

不是什么：不是运行平台（不提供线上对象查询、不执行业务动作、不写回客户系统），不是 BI，不是知识图谱平台，不是给终端业务用户自助用的工具。

## 2. 我们站在哪几层

按"语义建模、数据映射、对象查询、业务逻辑、动作执行、能力开放"这六层分：

| 层 | 我们的位置 |
|---|---|
| 语义建模 | 做。模型起草对象、识别字段、关系，代码用全部数据核验。 |
| 数据映射 | 做，但只到一次上传的范围：对象绑定到哪张表、按哪个字段识别、字段有没有去处。不做跨系统的持续同步。 |
| 对象查询 | 做，但只在这次上传的数据上：结构化查询由代码执行，支持计数、占比、多维分组。不做持久实例库。 |
| 业务逻辑 | 只有写死的几种算法（计数、占比、分组）。不做规则引擎、不做自定义计算。 |
| 动作执行 | 不做。 |
| 能力开放 | 不做。没有对外 API、没有下游消费者。 |

后两层不做的理由：还没有任何真实用户用过这个工具，更没有第二个系统要读我们产出的定义。等真的出现一个接收方和导入约定再谈。

每一层现在做到什么程度、用什么数据验证过，见 `FEATURES_2026-09-16.md` 与各轮 PRD 的执行记录。手上没有客户数据，验证一律用公开数据，见护栏里的"数据来源"。

## 3. 产出什么，谁用

一次工作走完，能带走三样东西，都是本机文件：

- 参考本体 JSON：人确认过的对象、关系、名字，带确认人、时间、来源文件和数据体检发现的识别字段问题。
- 验收问题：人和客户说定的 1–3 道题，存的是人已经看过、认可口径的那个查询。
- 本体和评测 JSON：这一次运行的全部结果。

谁消费：第一是同一位顾问下一次上传同一份文件时，系统自动拿它对照、并预填上次的判断；第二是拿去和客户开会、留档。**不是**可执行的运行时契约——保存一份定义不会让任何系统自动具备执行能力。

## 4. 一份定义的一生

起草 → 代码核验 → 数据体检与业务问答 → 人逐项确认 → 固定验收问题 → 下次重跑时的变更影响。

最后一环最容易被忽略，但它是这套东西有没有用的分水岭：下一版本体里对象改了名、字段没了、关系没了，系统必须说清哪些确认还成立、哪些验收问题受影响，而不是默默给个新答案，也不是把改名误判成失效。

## 5. 说话的规矩

这份文档和所有对外文案里，讲一项能力必须能回答三件事：做没做、验证到什么程度（用什么数据、什么时候、谁核的）、明确没做什么。写不出验证方式的，就算没验证，不能写成已验证。
