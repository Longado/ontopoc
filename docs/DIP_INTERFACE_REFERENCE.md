# 参照 DIP 平台：界面怎么组织，产出怎么对得上

2026-09-18。作者指示"界面的组成构成方式参考一下 DIP 平台"之后写的对照。

## 0. 材料从哪来，可信到什么程度

三份本机材料，都不是公开资料，这里只记结构，不抄客户内容：

- 一份**逐对象的界面配置操作手册**（本机 `.local-sensitive/DIP本体Demo-2026-08/docs/07-DIP界面配置操作手册.md`）。它是照着 DIP 界面一栏一栏写的填表说明，所以**每个对象要填哪几列是可信的**。
- 一份**导入与建模契约确认单**（同目录 `00-DIP导入与建模契约.md`）。它自己写明：批量导入的文件格式、主键规则、关系表达方式**全部"待实测"，没有和产品技术确认过**。所以"能不能直接导进去"这件事，现在谁都不知道。
- 一份**产品能力全景**与一份产品介绍 PPT，给出平台的整体分层和本体层的构成。

**结论先说**：DIP 的**表单长什么样**可信，**能不能自动导入**不可信。下面凡是涉及导入的，一律按"未确认"处理。

## 1. DIP 的界面是怎么组织的

平台按一条生命周期分段，PPT 里写的是五段：**数据接入前 → 数据接入 → 数据编排 → 本体建模 → 智能体编排**。

本体层内部分三块：**本体建模**（定义有哪些对象、每个对象有哪些属性）、**本体关系**（一对一 / 一对多 / 多对多，自动识别外键，力导向图谱，沿关系链下钻）、**对象管理**（对象实例的详情页，Excel 批量上传下载）。

它对本体层立了几条铁律，其中两条和我们直接相关：本体层**只放真实可接入的原始业务表**，不放"客户画像"这类分析层构造；**关系只用关系表达，实体表不冗余存关系**。

## 2. DIP 里建一个对象，界面要人填什么

每个对象一张表单：**业务本体中文名称 + 英文名称**，然后逐个属性填七列：

| 主键 | 展示 | 中文名称 | 英文名称 | 描述 | 类型 | 长度 |
|---|---|---|---|---|---|---|

几条硬规矩（手册原话的意思）：每张表**只有一个主键**；属性英文名必须和 CSV 表头**完全一致**；类型在 `VARCHAR / INT / DOUBLE / DATE / DATETIME / TEXT / BOOLEAN` 里选，还要填长度（编号 50、名称 200、枚举 50、说明 500、整数 11、金额 20）；主数据对象把 `name` 设成展示字段，交易对象把 ID 设成展示字段。

关系不当普通对象建，单独一张表导入：`关系ID / 源对象类型 / 源对象ID / 关系类型 / 目标对象类型 / 目标对象ID / 证据引用`。关系类型是大写动词，例如 `DEMANDS`、`AFFECTS`、`FULFILLS`、`RESOLVES`。

属性还分**属性类型**：主键 / 外键 / 数据导入 / 系统生成 / 计算字段 / 枚举值。

## 3. 我们现在产出什么，逐项对照

| DIP 表单要的 | OntoPoc 现在有没有 | 差在哪 |
|---|---|---|
| 对象的中文名 + 英文名 | 有。`label` 是中文名，`key` 实际就是英文名 | 对得上，只是没这么叫 |
| 属性的英文名 | 有，就是原表头 `path` | 对得上 |
| 属性的中文名 | 没有。表头是英文时（CMS 那份全是英文）没有中文对照 | 缺 |
| 属性的描述 | 没有 | 缺，且这本来就该人写 |
| 属性的类型 | **没有** | 缺。数据里每一列的值我们都读过，类型可以由代码算 |
| 属性的长度 | **没有** | 缺。同上，最长几个字是数出来的事实 |
| 主键 | 有，就是识别字段 | 对得上，但见下面第 4 条 |
| 展示字段 | **没有** | 缺。DIP 必填 |
| 属性类型（外键 / 计算字段 / 枚举） | 只区分识别字段和普通属性 | 缺外键标记；计算字段我们本来就不做 |
| 关系的两端和来源表 | 有（`from` / `to` / `source`） | 对得上 |
| 关系类型（大写动词） | 有 `label`（中文，如"属于""测量"） | 半对上，没有规范动词 |
| 关系基数（一对一 / 一对多 / 多对多） | **没有** | 缺。数据里数得出来 |

## 4. 三处真的对不上，其中一处是硬冲突

1. **多字段主键。** DIP 白纸黑字"每张表只有一个主键"。我们在 CMS 医院数据上真产出过一个靠两个字段识别的对象："医院质量措施结果"用 `Facility ID` + `Measure ID` 一起识别——这个建模是对的（一家医院的一个指标是一条），但它**填不进 DIP 的表单**。这是今天就能复现的硬冲突，不是猜的。
2. **字段类型和长度。** DIP 每个属性必填，我们一个都没有。
3. **关系基数。** DIP 的关系要选一对一 / 一对多 / 多对多，我们不给。

护栏里"关系基数、字段类型导出"这一条写的进入条件是"等有一个具体的接收方和导入约定"。**接收方现在有了（DIP），导入约定只有半个**（表单要哪几列是清楚的，批量导入怎么走没确认）。所以这一条的触发条件算**过了一半**。

## 5. 界面上该借鉴什么

**该借的一件事：把对象的属性从一句话变成一张表。** 我们现在在"看本体"的列表视图里把属性写成一行逗号串（`属性：a、b、c`），DIP 是一张七列的表。顾问下一步要做的事，就是照着这张表往 DIP 里填。把我们的列表视图改成同样的列（主键 / 展示 / 字段名 / 类型 / 长度 / 空值率），并且**类型和长度由代码从数据里算出来**，顾问就能直接照抄，而不是自己一列一列去数据里翻。

这件事的分量：代码算类型和长度不需要模型，也不需要拍任何阈值（最长几个字是数出来的）；它同时补上第 4 条里的三个缺口中的两个。

**顺带能补的：** 识别字段超过一个时，在那个对象旁边直接写"DIP 只接受单主键，导入前要合成一个主键或者改建模"。这是我们已经知道会咬人的地方。

## 6. 不该借鉴的

DIP 是**运行平台**，我们是**建模前的一道工序**，位置不同，下面这些照搬就是越界：

- 智能体编排、Action 执行、告警、接口回调——产品定义里写明不做。
- 权限口径、行列级权限——本机单人工具，不做权限中心。
- 对象实例详情页、实例库——我们只看这一次上传的数据，不做持久实例库。
- 计算字段（毛利率、OEE 这类口径）——那是业务逻辑层，我们只做到"代码算得出的计数、占比、求和、平均"。
- 多模态（音频、视频、地图、时序）、向量检索——一条都不碰。
- 按业务环节给本体分组（研发闭环 / 采购闭环 …）——那是行业模板的活，我们一次只看一份文件，分不出环节，硬分是编的。

## 7. 位置说清楚

照 DIP 的五段生命周期看，OntoPoc 站在**"本体建模"这一段的前面**：DIP 让人在表单里把对象和属性一条条配出来，我们做的是"从客户的数据里先看出这份表单该怎么填，并且逐行核验它填得对不对"。所以我们的产出天然应该长得像那张表单。

这也是第一次出现一个**点得出名字的下游消费者**。但要克制：导入约定还没和产品确认过，在确认之前，我们只做"把该填的列算出来给人看"，不做"一键导入 DIP"。
