# OntoPoc 迭代 3 需求：上传文件，自动生成公司本体并自动评测

> 状态：2026-09-14 起草，基线 main `9dc048d`。用户当天定向：主线从"召回范围研判"改为"上传一个文件 → 自动生成公司本体 → 自动评测"，召回研判留作内置示例场景。本文是当前唯一的迭代计划；`PRD_ITERATION_2.md` 转为历史记录（其中 M3 真人试用不再是主线）。

## 1. 为什么改

迭代 2 把一个公开数据场景做深了：自动搭本体、代码核验、名称对应、范围计算、复核回流。用户试用后的判断是太工程化，偏离了最初想要的东西：给一份公司的业务文件，系统自动搭出这家公司的本体，并且自动告诉你这个本体好不好。

迭代 2 里真正通用、值得带走的是：模型只看字段名和示例值提出本体；代码拿全部记录逐项核验，出错退回重做；判断必须附证据，代码核对证据真在原文里；稳定性要实测，不能凭感觉。召回场景专有的是四种角色、范围三类、召回前后、复核回流，这些留在示例里，不带进主线。

## 2. 开发前五行

```text
Pain：拿到一家公司的业务文件，手工梳理对象和关系要好几天，梳理完也说不清好不好。
Decision：这份自动生成的本体能不能拿去用（给客户看、接系统），哪里需要改。
Outcome：上传一个文件，几分钟内看到本体和三种评测结果，每项结果都能追到数据或原文。
Non-goals：账号与多人协作；在线部署；本体编辑器；把企业真实数据放进公开仓库；通用问答。
Smallest path：复用 public_ontology 的字段目录、代码核验、建图和退回重做循环（角色改为可选），
               复用 model_gateway、本机服务写法（recall_server）和现有页面框架。
```

## 3. 用户与场景

- **FDE / 实施顾问**：拿到客户给的一份 Excel 或制度文档，上传，得到本体和评测结果，拿去和客户对齐"你们的业务是不是这样"。
- **企业数据负责人**：想知道自家数据能不能撑起一个本体、缺什么字段、哪些关系连不上。

## 4. 需求

优先级：P0 本轮必须完成；P1 本轮做；P2 有空再做。

### F1 上传业务数据表，自动生成本体（P0）

- 支持 CSV、Excel（.xlsx，每个 sheet 当作一个来源）。
- 模型只看表头和每列少量示例值，提出对象类型（名称、身份字段、属性）、关系（哪两个对象、在哪张表里同时出现）和不用的字段；不再要求召回场景的四种角色。
- 代码拿全部行核验：字段存在、身份字段有值、多表之间同一对象用同样的身份键、每个字段都有去处、关系在数据里至少连上一条；出错把错误退回模型重做，没有进展或到第 3 次就停。
- 上传的文件只存在本机 `output/`，不进仓库。

验收：示例公司数据（见第 6 节）上传后得到通过核验的本体；构造数据的离线测试覆盖核验与退回。

### F2 上传业务文档，自动生成本体（P0）

- 支持 Markdown、纯文本、Word（.docx）、PDF（需要本机有 `pdftotext`）。
- 模型从文字里提出概念（名称、定义）和关系（谁与谁、什么关系），每一项都要引用原文；代码核对引用真在原文里，核对不上的剔除并列出来。
- 长文档按段落分块，每块一次模型调用，代码合并同名概念。

验收：示例公司的业务说明文档上传后得到概念和关系，每条都带可核对的原文引用。

### F3 自动评测一：本体和数据对不对得上（P0，代码计算）

- 数据表：字段覆盖（用上 / 标为不用 / 没去处）、身份冲突（同一身份在不同行里属性打架）、关系连通率（关系所在表里有多少行真的连上）、孤立对象（参与关系的类型里一条边都没有的对象）、多表是否连成一片。
- 文档：概念和关系的引用核对通过率、关系两端是否都是已提出的概念、没有任何关系的孤立概念。
- 每项给出数值和出处；可判对错的项（身份冲突为 0、每条关系至少连上一条、多表连通）标通过或不通过。不编造加权总分和分档。

### F4 自动评测二：能不能回答业务问题（P1，模型出题、代码执行）

- 模型根据本体为这家公司写一组管理者会问的业务问题，每题附一个结构化查询（从哪类对象出发、按什么属性筛选、沿哪些关系走、数数还是列出）。
- 代码在数据上执行每个查询：查询里的类型、关系、属性不存在就判"本体缺这一块"，执行出空结果就判"数据里没有"，有结果就给出答案和出处。
- 输出可回答的题数、不能回答的原因分布；这是"本体能不能支撑这些问题"，不是"答对率"。

### F5 自动评测三：与标准答案比对（P1）

- 上传一份参考本体（JSON，格式与导出的本体相同或更简），代码按身份字段和名称匹配对象类型，按两端匹配关系，给出命中、漏掉、多出的清单和条数。
- 示例公司数据附一份人工写的参考本体，作为回归样本。

### F6 页面（P0）

- 主入口改为"上传建本体"：上传 → 本体 → 评测三个标签页；本机服务没启动时，可以打开内置的示例结果看效果。
- 召回研判收为"示例：汽车召回"入口，不再加功能；事件 95876 入口保留。
- 首页与 README 改讲新主线。

### F7 表格和文档一起用（P2）

文档里的概念对齐到表格里的对象（模型提出、代码核验），让文档补上表格没有的定义和规则。

## 5. 非功能要求

- 模型调用：提示词带版本号，temperature 0，结构化输出逐字段校验，每次记录模型名和提示词版本；循环、重试、停止都在代码里。
- 评测一、三全部由代码计算；评测二只让模型出题，判定由代码执行查询完成。
- 公开仓库：只放合成的示例数据；企业文件和运行结果留在本机 `output/`（已被 git 忽略）。
- 页面在 1440 宽和 390 宽下可用。

## 9. S1 结果（2026-09-14）

- 上传 CSV / Excel → `company_sources.load_table_file` 转成来源包（每个 sheet 一张表，日期转 ISO，文件不超过 10 MB）。
- 建模器加了"公司"模式（`company_ontology.py`，提示词 `company_ontology_modeler.v1`）：不要召回的四种角色，其余核验与退回重做沿用；召回模式的行为和测试不变。
- 评测一（`ontology_eval.data_fit`，纯代码）：字段去处、同一对象信息打架、引用找不到、关系连通行数、孤立对象、表的连通，五项可判对错的检查标通过或不通过。"引用找不到"只看给出属性的那张表（例如客户表），客户没下过单不算问题。
- 本机服务 `ontology_server`（端口 8767，只收本机请求，结果存 `output/ontology-runs/`）；命令行 `scripts/run_company_ontology.py`。
- 页面默认入口改为"上传建本体"：上传、本体、评测三个标签页，本机服务没开时可以打开内置示例；召回研判和 95876 收为示例入口。
- 合成示例 `examples/company/demo_company.xlsx`（`scripts/make_demo_company.py` 生成，客户 31、产品 12、订单 160、售后工单 45 行，故意放了两个问题）。两次用 DeepSeek 实跑：
  - 命令行一次：第 2 次提交通过，5 个对象、4 条关系（含"售后工程师"），存为页面示例。
  - 页面上传一次：46 秒，第 2 次提交通过，4 个对象、3 条关系（工程师留作工单属性）。
  - 两次评测一都抓到两个故意放的问题：客户 KH012 城市一个写合肥、一个写苏州；订单引用的 KH099 不在客户表里。两次本体不同，这正是评测三要比对的东西。

## 10. 模拟用户试用后的五步改进（2026-09-14）

三个模拟用户（实施顾问、数据治理负责人、售后总监）测完 S1 后，按监督结论的顺序做了五步。每一步都先写失败测试、再实现，并用 DeepSeek 在页面上实跑过。

1. 小修：
   - 表头上方的标题行自动跳过并显示出来（此前"2026年采购明细"被当成表头，字段名成了"列4"）；没有表头、也没有值的空列直接去掉。
   - 同一个编号有几种写法（大小写、首尾空格）会单独报出来，成为第 6 项检查；去掉前导零后相同的编号列为"疑似重复，请人工确认"。
   - 标签改为"本体结构已通过核验"，并注明它不代表数据干净。
   - 模型请求失败返回"请重试"，不再显示成"本体没通过"。
   - 结果页显示建模目的。
   - 顺带更正：上次汇报说"退回原因已改成中文"，其实那次改动因为 `cd` 失败没执行，这次才真正改好。
2. 本体页改成早期方案的样子：关系图居中（自己画的 SVG，没有加回 React Flow，公司本体通常只有 4–15 个对象）；右侧证据检查栏；评测发现的问题直接标在节点上，问题是红色、提示是黄色；关系线上写模型给的中文短名（建模提示词 v2）；跨列的关系线从上方绕过；大图在画布里横向滚动，不再缩到看不清。
3. 评测二（`ontology_questions.py`，提示词 `company_questions.v3`）：一次模型调用写出一组问题和结构化查询，代码在数据上执行。
   - 答不了时分三种写明："本体缺这一块"、"数据里没有"、"查询写法表达不了（不是本体的问题）"。
   - 还能自己提问；证据栏底部有"询问这个本体"入口。
   - 实跑时出过两处我自己的设计问题，都已修掉：模型把字段写成"对象名.字段"，第一版全被判成本体缺，改为三种写法都认；同时按两个维度分组的问题，被错算到本体头上。示例数据上最后是 6 题答 5 题，剩下 1 题是查询写法表达不了。
4. 稳定性和评测三（`ontology_compare.py`）：按"读同一张表、用同样的身份字段"对应对象，名字不同也能对上。同一份文件再上传，会自动列出和上一次相比多了、少了什么；上传人写的参考本体可以逐项比对。示例参考本体见 `examples/company/demo_reference_ontology.json`；一次实跑是对象 5/5、关系 4/4，另一次少了"售后工程师"，两次之间的差别页面会直接写出来。
5. 文档上传（`company_documents.py`，提示词 `company_document_modeler.v1`）：Markdown、文本、Word、PDF 按段分块，每块一次模型调用，每一项都要引用原文，代码核对不上的剔除；最多处理 12 块，超出时页面写明。文档的评测一改为文档检查，评测二不适用，评测三照常。合成的售后服务流程文档实跑：17 个概念、25 条关系，全部核对通过。

还没做：表格和文档一起用（F7）；真实公司文件试用（等用户提供）。首页改讲新主线已在第 11 节完成。

## 11. 界面与交互一轮（2026-09-15）

用户要求改善界面设计和交互，再请三个人测。先改四步，再请交互设计师、第一次用的非技术运营负责人、高频使用的实施顾问三位模拟用户在真实服务上测（1440 与 390 两种宽度，各自真上传），每条发现都回到代码或保存的结果里核实后才改。

先改的四步：

1. 上传页：拖放区、文件卡片、建模目的加示例问题、按服务实时回报的分步进度（读取、模型提出、代码核验、自动评测）、右侧示例入口和示例文件下载。建模改成后台任务，页面每秒查询一次进度。
2. 结果总览：顶部五张卡片（本体、数据体检、业务问答、对照标准、稳定性），点哪张直接到对应页；评测拆成三个子页；数据问题旁有"在图上看"，问答旁有"在图上看路径"；答案用条形图；模型名、提示词版本收进"技术信息"。
3. 关系图：点对象只亮它和相连的对象，其余变淡；查询路径高亮并在右栏写明每一步经过哪条关系；图例；从评测跳过来时自动滚到图和对应对象。
4. 首页改讲"上传一份业务文件，得到公司本体和它的体检报告"，四个数字都来自示例公司的真实运行；召回研判改为示例场景；边界里写明建模时会把字段名和少量示例值发给模型。

测出来、核实后改掉的：

- 真上传报 "Unknown ontology endpoint"：本机建模服务是加后台任务之前启动的旧进程，没重启。重启后正常；页面遇到 404 改为提示重启服务，不再显示英文原文。改了后端就要重启建模服务。
- 同一份文件第三次上传被判"本体没通过"：退回重做的停止条件是"错误数没减少"，模型改掉了第一处错、又冒出另一处，数量相同就停了，第三次机会没用上。改成"一处都没改掉才停"。
- "哪些客户经常延期交货"：查询其实只数了交货状态为"延期交货"的订单，但"怎么查的"没写筛选条件。现在写成"只看'交货状态'为'延期交货'的订单 → …"；示例结果里同类的一题也按新写法重算（答案不变）。算占比、同时按两样东西分组，现在的查询还做不到，页面照实写"这种问法还不支持，本体本身没问题"。
- 重跑差别"完全一致"被质疑：那次比的是另一位测试者刚上传的同一文件，比较本身没错，但页面没说比的是哪一次。现在写明上一次的本机时间（之前显示的是 UTC）、建模目的和对象、关系数；目的不同时提示差别可能来自目的。首页相应的一句也补上了"建模目的写得不一样"。
- 页面副标题和首页说三项评测都自动，其实问答要手点：改成数据表建完自动出一轮题并用数据回答（进度里显示这一步）；对照标准要有人写的参考本体，页面写明"上传参考本体后可以比"。
- 刷新后像是结果没了：结果其实还在本机浏览器里，只是回到了上传页。现在刷新后直接打开上一次的结果，上传页也提示"上一次的结果还在"。
- 示例结果里问答输入框看着能点其实不能：改为直接说明"这是示例结果，只能看"，并给"上传自己的文件"按钮。
- 其他：选错类型或空文件在上传前就提示；拖放区键盘焦点可见（之前的样式挂错了元素）；图里键盘焦点加粗；手机上关系图和表格有滚动阴影、图上写"左右滑动看全图"；总览卡片加一句"这个数算好还是差"；业务问答的数把自己问的题也算进去；"代码退回 1 次"改成"模型改了 1 次后通过核验（第 1 版：原因）"；页头解释"本体"是什么；参考本体用和上传页一致的按钮；下载文件改名"本体和评测"（内容本来就包含三项评测）。

测试者说错、没改的：实施顾问说刷新后第 2、3 步变成不可点，截图里其实是可点的；设计师说下载只有本体结构，文件里其实有三项评测，只是文件名误导。

还没做：非技术用户仍会问"同一份文件为什么两次不一样"，页面已如实写出差别，但怎么让人放心（例如多跑几次取共同部分）还没设计；算占比、多维分组的问法。

## 12. 接下来三轮（2026-09-15 定）

用户同意按这三件做计划并执行：两次结果不一样敢不敢信、补上不支持的问法、真实公司文件试用。真实文件要等用户提供，所以顺序是 A → B → C 的准备部分，文件到了再做 C 的试用。三轮在一个分支上，每轮先写失败测试、再实现、再用 DeepSeek 在页面上真跑，结束时请一位对应背景的模拟用户复测，发现回主线核实后再改；三轮做完一起开 PR，合并前问用户。

### A. 稳定性：多跑几次，看哪些靠得住

- 要做到：数据表上传后，服务除了这一次，再并行建两次本体（共三次，同时发出，墙钟时间约等于一次）。代码按"读同一张表、用同样的识别字段"把三次的对象和关系对齐，给每个对象、每条关系标"三次都有"或"三次里有一次"。图上不稳定的对象画虚线框，右栏写出现了几次；总览的稳定性卡片改成"4 个对象三次都有，1 个时有时无"。数据体检和问答仍然基于第一次的本体。三次是产品上的选择（能分出"都有 / 多数 / 少数"），写成服务里的一个常量，页面写明跑了几次。
- 不做：把三次合成一个新本体（只标注，不合成）；问答的稳定性；文档（文档按段每段一次调用，三倍成本另议）。
- 改哪些：新文件 `ontology_stability.py`（按对象、关系统计出现次数，复用 `ontology_compare` 的对齐规则）；`ontology_server.finish_build`（并行建、进度里显示"另外两次"）；图和总览的前端模型与组件。
- 证明：假模型给出三份不同的提议，测试出现次数与标注；真跑示例公司，看"售后工程师"这类时有时无的对象被标出来。

### B. 问法：占比和多个维度分组

- 要做到：结构化查询多两种写法。一是 `group_by` 可以写多个字段，按组合分组；二是"占比"，每组里满足某个条件的比例，页面同时显示分子分母（例如"2 / 2，100%"），按占比排、分母一起给出，不设最少样本数的门槛，小分母让人自己看。提示词升到 `company_questions.v4`。示例公司"哪些客户、产品的售后问题最多"应能回答；"哪些客户经常延期交货"答成延期占比。示例结果重新生成一轮问答。
- 不做：求和、平均（例如订单金额）；时间窗口（例如"最近三个月"）。这两类照旧标"这种问法还不支持"。
- 改哪些：`ontology_questions.py`（执行与提示词）、前端答案展示与路径文字、示例结果。
- 证明：在测试数据上验多维分组和占比的数；真跑示例公司和一份延期交货样例表。
- 复测：实施顾问，问一组带比例和交叉分组的问题。

### C. 真实公司文件试用

## 13. 定位收窄与逐项确认（2026-09-15）

回看后定的：OntoPoc 是"给实施顾问和本体团队用的本体起草与体检工具"，卖点不是"自动建本体"，而是每一处都有证据、并如实标出哪里靠不住。改动：

- GitHub 描述和 topics、README 中英文开头改讲这个定位；标语改为 "Draft the ontology. Show the evidence."，Logo 图里的旧标语去掉，只留图标和字样；召回研判和 95876 收进左侧"更多示例"。
- 逐项确认：自动评测里真正有外部依据的只有"对照标准"，但现实里几乎没人手里有参考本体。现在顾问可以在关系图右栏或列表里给每个对象、每条关系点"对 / 不对"，改名，补上漏掉的对象；保存后这份判断就是这个文件的参考本体（存在本机 `output/ontology-runs/references/`，按文件 sha256），马上对照一次，同一份文件以后再上传自动对照，也能下载成参考本体 JSON。判"对"的关系会把两端也判"对"，判"不对"的对象会连带它的关系；对照页把"你判为不对的"和"还没判断的"分开列。
- 关系线加了一层看不见的加宽点击区（原来 2 像素很难点中）。
