# OntoPoc 迭代 3 需求：上传文件，自动生成公司本体并自动评测

> 状态：2026-09-14 起草，基线 main `9dc048d`。用户当天定向：主线从"召回范围研判"改为"上传一个文件 → 自动生成公司本体 → 自动评测"，召回研判留作内置示例场景。本文是当前唯一的迭代计划；`PRD_ITERATION_2.md` 转为历史记录（其中 M3 真人试用不再是主线）。

## 1. 为什么改

迭代 2 把一个公开数据场景做深了：自动搭本体、代码核验、名称对应、范围计算、复核回流。用户试用后的判断是太工程化，偏离了最初想要的东西：给一份公司的业务文件，系统自动搭出这家公司的本体，并且自动告诉你这个本体好不好。

迭代 2 里真正通用、值得带走的是：模型只看字段名和示例值提出本体；代码拿全部记录逐项核验，出错退回重做；判断必须附证据，代码核对证据真在原文里；稳定性要实测，不能凭感觉。召回场景专有的是四种角色、范围三类、召回前后、复核回流，这些留在示例里，不带进主线。

## 2. 开发前五行

```text
Pain：拿到一家公司的业务文件，手工梳理对象和关系要好几天，梳理完也说不清好不好。

Non-goals：账号与多人协作；在线部署；本体编辑器；把企业真实数据放进公开仓库；通用问答。
Smallest path：复用 public_ontology 的字段目录、代码核验、建图和退回重做循环（角色改为可选），
               复用 model_gateway、本机服务写法（recall_server）和现有页面框架。
```

## 3. 用户与场景

- **FDE / 实施顾问**：拿到客户给的一份 Excel 或制度文档，上传，得到本体和评测结果，拿去和客户对齐"你们的业务是不是这样"。
- **企业数据负责人**：想知道自家数据能不能撑起一个本体、缺什么字段、哪些关系连不上。

## 4. 需求

优先级：P0 本轮必须完成；P1 本轮做；P2 有空再做。

### F1 上传业务数据表，自动生成本体（P0）

- 支持 CSV、Excel（.xlsx，每个 sheet 当作一个来源）。
- 模型只看表头和每列少量示例值，提出对象类型（名称、身份字段、属性）、关系（哪两个对象、在哪张表里同时出现）和不用的字段；不再要求召回场景的四种角色。
- 代码拿全部行核验：字段存在、身份字段有值、多表之间同一对象用同样的身份键、每个字段都有去处、关系在数据里至少连上一条；出错把错误退回模型重做，没有进展或到第 3 次就停。
- 上传的文件只存在本机 `output/`，不进仓库。

验收：示例公司数据（见第 6 节）上传后得到通过核验的本体；构造数据的离线测试覆盖核验与退回。

### F2 上传业务文档，自动生成本体（P0）

- 支持 Markdown、纯文本、Word（.docx）、PDF（需要本机有 `pdftotext`）。
- 模型从文字里提出概念（名称、定义）和关系（谁与谁、什么关系），每一项都要引用原文；代码核对引用真在原文里，核对不上的剔除并列出来。
- 长文档按段落分块，每块一次模型调用，代码合并同名概念。

验收：示例公司的业务说明文档上传后得到概念和关系，每条都带可核对的原文引用。

### F3 自动评测一：本体和数据对不对得上（P0，代码计算）

- 数据表：字段覆盖（用上 / 标为不用 / 没去处）、身份冲突（同一身份在不同行里属性打架）、关系连通率（关系所在表里有多少行真的连上）、孤立对象（参与关系的类型里一条边都没有的对象）、多表是否连成一片。
- 文档：概念和关系的引用核对通过率、关系两端是否都是已提出的概念、没有任何关系的孤立概念。
- 每项给出数值和出处；可判对错的项（身份冲突为 0、每条关系至少连上一条、多表连通）标通过或不通过。不编造加权总分和分档。

### F4 自动评测二：能不能回答业务问题（P1，模型出题、代码执行）

- 模型根据本体为这家公司写一组管理者会问的业务问题，每题附一个结构化查询（从哪类对象出发、按什么属性筛选、沿哪些关系走、数数还是列出）。
- 代码在数据上执行每个查询：查询里的类型、关系、属性不存在就判"本体缺这一块"，执行出空结果就判"数据里没有"，有结果就给出答案和出处。
- 输出可回答的题数、不能回答的原因分布；这是"本体能不能支撑这些问题"，不是"答对率"。

### F5 自动评测三：与标准答案比对（P1）

- 上传一份参考本体（JSON，格式与导出的本体相同或更简），代码按身份字段和名称匹配对象类型，按两端匹配关系，给出命中、漏掉、多出的清单和条数。
- 示例公司数据附一份人工写的参考本体，作为回归样本。

### F6 页面（P0）

- 主入口改为"上传建本体"：上传 → 本体 → 评测三个标签页；本机服务没启动时，可以打开内置的示例结果看效果。
- 召回研判收为"示例：汽车召回"入口，不再加功能；事件 95876 入口保留。
- 首页与 README 改讲新主线。

### F7 表格和文档一起用（P2）

文档里的概念对齐到表格里的对象（模型提出、代码核验），让文档补上表格没有的定义和规则。

## 5. 非功能要求

- 模型调用：提示词带版本号，temperature 0，结构化输出逐字段校验，每次记录模型名和提示词版本；循环、重试、停止都在代码里。
- 评测一、三全部由代码计算；评测二只让模型出题，判定由代码执行查询完成。
- 公开仓库：只放合成的示例数据；企业文件和运行结果留在本机 `output/`（已被 git 忽略）。
- 页面在 1440 宽和 390 宽下可用。

## 6. 示例数据

一份合成的"示例制造公司"数据（明确标注为合成）：客户、产品、订单、售后工单四张表，放进一个 Excel；一份售后服务流程说明文档；一份人工写的参考本体。它们既是演示材料，也是离线测试和回归的固定样本。

## 9. S1 结果（2026-09-14）

- 上传 CSV / Excel → `company_sources.load_table_file` 转成来源包（每个 sheet 一张表，日期转 ISO，文件不超过 10 MB）。
- 建模器加了"公司"模式（`company_ontology.py`，提示词 `company_ontology_modeler.v1`）：不要召回的四种角色，其余核验与退回重做沿用；召回模式的行为和测试不变。
- 评测一（`ontology_eval.data_fit`，纯代码）：字段去处、同一对象信息打架、引用找不到、关系连通行数、孤立对象、表的连通，五项可判对错的检查标通过或不通过。"引用找不到"只看给出属性的那张表（例如客户表），客户没下过单不算问题。
- 本机服务 `ontology_server`（端口 8767，只收本机请求，结果存 `output/ontology-runs/`）；命令行 `scripts/run_company_ontology.py`。
- 页面默认入口改为"上传建本体"：上传、本体、评测三个标签页，本机服务没开时可以打开内置示例；召回研判和 95876 收为示例入口。
- 合成示例 `examples/company/demo_company.xlsx`（`scripts/make_demo_company.py` 生成，客户 31、产品 12、订单 160、售后工单 45 行，故意放了两个问题）。两次用 DeepSeek 实跑：
  - 命令行一次：第 2 次提交通过，5 个对象、4 条关系（含"售后工程师"），存为页面示例。
  - 页面上传一次：46 秒，第 2 次提交通过，4 个对象、3 条关系（工程师留作工单属性）。
  - 两次评测一都抓到两个故意放的问题：客户 KH012 城市一个写合肥、一个写苏州；订单引用的 KH099 不在客户表里。两次本体不同，这正是评测三要比对的东西。
