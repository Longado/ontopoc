# 公开召回场景 · 缺点研判与下一轮计划（2026-09-13）

> 四个只读 agent 分别从场景与产品、数据与范围逻辑、模型调用与通用性、代码审查四个角度找问题；下面每一条都在主线用代码或数据重新核对过，"核对"一列写明结果。agent 说过头或数字不对的地方已改正或剔除。

## 1. 核对后的问题清单

### A. 答案不完整：该看的投诉没进候选

| # | 问题 | 核对 |
|---|---|---|
| A1 | 两边部件名称写法不同就连不上。刹车：召回写"SERVICE BRAKES, HYDRAULIC"，投诉写"SERVICE BRAKES"，两个刹车召回 0 条候选，而带 SERVICE BRAKES 的投诉有 34 条。动力：60 条投诉只标了"FUEL/PROPULSION SYSTEM"，与电池召回的"ELECTRICAL SYSTEM:PROPULSION SYSTEM"连不上 | 属实。60 条里 32 条提到 battery，但只有 1 条标起火，多数是失去动力；它们该不该算进电池召回是判断问题，agent 说"藏掉约 94 条真实起火投诉"过头 |
| A2 | 只标"UNKNOWN OR OTHER"的 46 条投诉任何召回都不会考虑，页面没有提示这个盲区 | 属实（全部 679 条里 367 条从未成为任何召回的候选，多数确实无关，如转向 122 条） |

### B. 答案会误导

| # | 问题 | 核对 |
|---|---|---|
| B1 | 两个来源日期格式不同：召回 `ReportReceivedDate` 是日/月/年（30/08/2018），投诉日期是月/日/年（11/14/2018），页面上并排显示、没有说明 | 属实；任何比较先后的逻辑都必须先按来源解析 |
| B2 | "所有同类召回之外"把召回发布前和发布后的投诉混在一起。21V650000 的 43 条全在召回之后；24V812000 的范围外是召回前 21 条、召回后 22 条 | 属实（agent 给的是 23/20，按正确日期格式重算为 21/22） |
| B3 | 同一缺陷的连续召回被当成互不相关的"其他召回"。电池 5 个召回都指向同一部件，24V481000、24V812000 的原文写明是 21V-650 修复失败后的再召回；选召回时 13 个按钮实际是 4 组重复加 2 个独立的 | 属实。更正：5 个电池召回的 287 条候选相同，但按覆盖年款分成两组（2017–2019 与 2020–2022），分类分布不同，不是 agent 说的"完全一样" |
| B4 | 投诉里的非车辆条目被当成车型：7 条投诉带轮胎、充电设备或 NHTSA 测试占位（如"TBD TBD 9999"），直接显示在页面上 | 属实；不影响分类结果，但显示错误 |
| B5 | 页面开头写"召回 42 条记录"，能选的召回是 13 个（42 是召回 × 年款的行数） | 属实 |

### C. 质量工程师用起来卡在哪

| # | 问题 | 核对 |
|---|---|---|
| C1 | 13 个召回里只有 2 个有模型初判（1517 条候选中 310 条） | 属实 |
| C2 | 列表按投诉编号排序，起火、碰撞、召回后才出现的投诉看不出来（21V650000 范围外 43 条里起火 2、碰撞 3） | 属实 |
| C3 | 直接显示原始字段名（`products[].manufacturer`、`dateComplaintFiled`）；"本体""信号"等词质量岗看不懂 | 属实 |
| C4 | 下载的复核结果不含日期、起火、碰撞，拿出去说明不了理由 | 属实 |

### D. 模型判断的可靠性

| # | 问题 | 核对 |
|---|---|---|
| D1 | 请求里没设 temperature，模型名 `deepseek-flash` 是别名，重跑结果会漂 | 属实 |
| D2 | 证据检查只看"是不是原文片段"，模型交一个"the"也能通过 | 属实（代码 `public_scope.py:143`） |
| D3 | 判断原文时拿不到部件名：本体里"部件"对象没有任何属性，召回描述只来自召回文本 | 属实 |
| D4 | 没有回归样本：换提示词版本时没有固定样本比对 | 属实；复核页的人工标注就是来源，差一步把它变成固定样本 |
| D5 | 本体重试只有"没进展就停"，没有次数上限 | 部分认同。"没进展就停"本身符合契约；契约另有"单次操作最多串 3 次模型调用"，据此加上限 3 次 |

### E. 代码完整性（代码审查，均已复现）

| # | 问题 |
|---|---|
| E1 | 高：召回来源为空时，打包不再核对"本体是不是用这份数据建的"，照样产出 0 个召回的页面数据 |
| E2 | 中：投诉原文判断函数不核对数据版本，传入被改过的数据也照常运行 |
| E3 | 中：构建快照时直接引用调用方的记录对象，调用方之后改了原对象，快照跟着变 |
| E4 | 中：打包时对象图重建 14 次（每个召回一次 + 开头一次） |
| E5 | 低：页面数据校验只查顶层，缺某条投诉时页面会白屏而不是报错 |

### F. "自动搭建本体"的边界（如实说明，不在下一轮扩建）

四个角色写死、跨来源只做精确字符串匹配、通用模块依赖名为 `nhtsa_sources` 的模块、在线脚本写死 `campaign_number`、页面写死 `Summary` 字段。用单一来源的 openFDA 数据按合理方式写本体，核验直接报 `role_count`。结论：它是"召回 × 投诉范围研判"的自动搭建，不是任意问题的本体平台。README 与方案文档已这样写；D 轮换车型、换来源时再按实际需要放开，不提前建平台。

### 已排除的方向（不用再查）

- 逗号拆分会拆坏部件名：112 种投诉部件组合里没有一个名称自带逗号。
- 召回正文年份与结构化年款不一致：13 个召回全部一致（20V811000 正文里的 2021 年是同一公告里的其他车型）。

## 2. 下一轮：让电池和刹车这两个问题的答案可信

**场景：** 质量工程师要回答"召回范围之外，哪些同类投诉需要上报"。这一轮只做让这个答案完整、不误导、排得出先后的事。

**Outcome：** 打开电池召回，看到的是按"召回后、起火、碰撞"排好序的范围外投诉，每条标明是召回前还是召回后；刹车召回不再是 0 条；连续召回显示成一条有先后的系列；页面上没有把轮胎当车型。

| 步 | 做什么 | 验收 |
|---|---|---|
| 1 | 修 E1–E3：打包和原文判断都先核对数据版本；快照拷贝记录 | 先写复现测试（召回为空、数据被改、改原对象），修完通过 |
| 2 | 日期：NHTSA 适配器声明每个日期字段的格式，代码拿全部记录验证每个值都能按声明解析，统一成 ISO 日期再进入计算和显示 | 召回日期与投诉日期各有一个测试样本；任一值解析失败就拒绝建快照 |
| 3 | 时间维度：每条候选标"召回前 / 召回后"与间隔天数；每类列表按"召回后 → 起火 → 碰撞 → 提交日期新到旧"排序（纯代码） | 21V650000 范围外 43 条全部标"召回后"；24V812000 为 21 / 22；列表第一屏能看到起火条目 |
| 4 | 跨来源取值对应：模型根据两边的取值清单提出"召回里的 X 对应投诉里的 Y"，代码逐条算这条对应能多连上多少条记录，零新增的对应拒绝；通过的对应在确认本体时逐条展示，经对应连上的候选在页面上标"经名称对应" | 刹车召回出现候选（上限 34 条带 SERVICE BRAKES 的投诉）；FUEL/PROPULSION 是否对应电池由模型提出、人确认，结果如实记录 |
| 5 | 召回系列：部件相同的召回按日期排成一条系列，原文里"previously remedied under recall number …"用正则提取（不用模型）；选召回按系列显示，"其他召回已覆盖"写明是同一系列的哪一次、何时 | 选召回列表显示 6 组；24V812000 显示"21V650000 修复后再召回" |
| 6 | 非车辆条目：本体的数据来源允许写一个取值条件（如 `products[].type` 等于 Vehicle），代码核验条件字段存在且过滤后仍有记录 | 7 条带非车辆条目的投诉不再显示假车型 |
| 7 | 重跑在线：电池、刹车两个系列的原文判断（请求设 temperature 0，把部件名加进判断输入），重建页面数据；页面开头改成"13 个召回、679 条投诉" | 在线报告与页面数据 `--check` 通过；浏览器走一遍电池、刹车 |

**本轮不做：** 其余召回系列的原文判断、字段中文名与导出字段、证据长度规则、换车型、任意问题的本体平台、模糊匹配引擎。

## 3. 再下一轮：给一位质量岗用 30 分钟

- 字段中文名对照（约 10 个字段）；列表显示起火 / 碰撞 / 召回后标记；下载结果带日期、起火、碰撞、所属系列。
- 其余 4 个系列跑原文判断，页面每个召回都有初判。
- 用第一位质量岗的复核结果做固定回归样本：以后改判断提示词，先在这批样本上比对一致数，再上线。证据检查是否要加规则，由这批样本里的实际错判决定。
- 找一位质量岗从电池系列的范围外投诉开始复核，记录用时、改判条数、他们认为缺的信息。
