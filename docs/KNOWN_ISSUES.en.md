# Known issues

Moved from the [README](../README.en.md). Issues that belong only to the earlier screen (`legacy.html`) are in [LEGACY_SCREEN.en.md](LEGACY_SCREEN.en.md#known-issues).

- **Questions about a relation between objects of the same kind have no direction yet.** Relations such as employee reports-to or parent-child organisation can be modelled, verified and exported; but a question cannot say superior or subordinate, so it states the limit and stops.
- **The relation check only requires one connected row.** In the data check, a relation passes as soon as it connects one row, even if the share of rows that connect is very low; the page states how many rows connect, so look at that number.
- **Definitions and joins are narrow.** A code meaning covers a few values of one column; a repeated number has three ways to be read; a join has only input, join and output steps and refuses to run past a row cap; the name-versus-calculation check knows only P50, P90, mean, total, max and min, and needs a same-named source column in another table. All of this has been tried only on synthetic planted tables and public data, never on a real client's data.
- **Value rules are narrow.** A rule is on one object type only (never across types), on a property of its own dataset (not on a derived property), and is one of a fixed few: not empty, a comparison with a number or a range of numbers, one of the codes with a meaning, one date not before another of the same type. Comparisons are with numbers only, not with a fixed date; no formula, no rule engine, at most 20 rules per type. Rules are not yet exported as SHACL. Measured on 150,000 rows with 10 rules on one Mac: the rule pass takes about 0.8 s, run before a recheck or a group confirmation takes the write lock; tried on synthetic data only. The count of items to confirm, the type list and the review queue list do not count rules on every page: they use the count kept by the type's last proposal, confirmation or recheck, so a waiting type whose data got a new version is left out of the count until someone opens it (opening it keeps the count it makes). Counting reads the rows without a write lock, but the workspace file uses SQLite's rollback journal, so while a count runs another writer's commit waits for it (as long as the count takes: 0.3 to 0.8 s measured on 150,000 rows with 10 rules, on the type page, a proposal or a confirmation; moving to SQLite's write-ahead log would end this and is not done).
- **An older version of OntoPoc on a file with value rules ignores them.** Run on such a file, a version without value rules opens it, keeps the rules through an edit of a type's name or description, drops them on an edit of its key or properties (the type then waits for confirmation again), does not count them on an upload, and lets a person confirm a type whatever its rules say. This version trusts a confirmed type's rules only when the latest count it kept was made on the type's current data, for its current rules and codes, and shows no broken row. Until that holds, every page and readout that shows or uses the type (the type list, the explorer, boards, questions, the agent's readouts, the OWL and SHACL download) shows it as needing another look and does not use it. Deciding this counts nothing; a board or an explorer page opened by a builder still counts the rules of a type that waits, each time, to show how many rows break each. The count is made once the service has started (after the port is open), when someone opens the type, and before the first question or agent readout that would use it: a type with no usable count is counted, and one with a broken rule is sent back, telling the people who can confirm it once. A count that fails sends the type back saying its rules could not be checked; the service and other requests carry on.
- **The "Counts repeated rows" mark does not reach everywhere.** It looks only at joins inside pipelines: a table uploaded already joined, or joined elsewhere and pulled in, carries no mark and can still add up too high. Across pipelines the mark does not come off: a later pipeline that dedupes on the order key is still refused (it has none of the earlier join's row columns), so it may refuse more than it needs to. Two right numbers are refused too: the max amount grouped by customer and the average amount grouped by order stay marked, so a sum over those tables is refused (what cannot be proved stays). A column the aggregate groups by alone carries no mark (each value is on one row). A "latest" statistic and a one-to-one lookup still answer: copies do not change them. After an upgrade, each pipeline output with a join written by an earlier version answers only once its pipeline has run again (see the README); until then its checked numbers show as refused rather than "needs another look" (a checked number has no such state), and its questions we need go back to "needs another look".
- **One service process per workspace file.** Counting and judging value rules is done one at a time within one process; two processes on the same file may each count the same type.
- **Answer checks rely on the model declaring honestly.** Code checks that the query that ran matches how the model said it read the question; if the model misstates the reading and the query happens to match, the check cannot see it. The query language can say "equals a value", "is none of these values", numeric and date ranges (see [QUERY.md](QUERY.md)), and the top or bottom N.
- **The same plain question can be read two ways.** For "What is sales?" the model may count every row or only a confirmed view, so the main number can differ between two asks; both numbers are shown when the model answers on all rows or includes the view by name; when it writes the view's conditions out itself, only its number is shown.
- **Other names are heard only as written.** A name or other name with Chinese in it is found anywhere in a question, one in letters only as a whole word (an English name also in its plural or singular); other names ignore case and full or half width. A misspelling, or a synonym nobody wrote down as an other name, is not heard, and then the model's reading decides. An other name found only inside a longer name of another definition is not heard there (on the demo, Customer's other name 客户 inside the property's 客户号).
- **A definition's own name is heard even inside a longer name, as before.** Where the short one is a name, not an other name, it is never muted: the pilot's type 客户 inside a property's other name 客户号 is heard, so "客户号C015的订单有几笔？" is refused while that type waits, as main refuses a name inside a longer name. A short name can still be heard inside a word that is no name of anything: that only ever refuses, never changes a number. OntoPoc Query does not take other names: it names types and relations by their name or English name.
- **A question that names a view the model does not read is refused, even when the model's own filter is right.** "Amount of the orders that are not valid orders" with the model leaving out Paid, Shipped and Delivered is refused because the question names Valid orders (by its name or an other name) and the query does not read it; so is a question naming the view and a meaning together, answered by grouping. The refusal says why; ask without the view's name.
- **A condition the model leaves out is not caught.** When the question asks for part of the rows and the model writes no condition, the answer covers every row.
- **"Lowest" ranks only groups that have rows.** "The customer with the lowest order total" ranks customers that have orders; a customer who never ordered is not among them.
- **A real model's answers vary.** Asked the same question several times, it now and then writes a query code refuses (a refusal, not a wrong number). Each round ends with `scripts/real_model_check.py`, which checks answers on the bundled data against SQL.
- **"Needs another look" is judged by share of the table.** A value's rows must more than double or fall below half, and by at least 5 rows. These two numbers are chosen, not measured; a shift smaller than that goes unnoticed.
- **Code finds only some missing relations.** Removing each relation in turn on 17 saved runs (public and synthetic data), it found 24 of 33 again; on complete ontologies it has not suggested a false one.
- **Queries cannot yet** work out two different numbers in one question (a total and an average, say), or say which things tend to appear together. It says so when asked. Filtering by a numeric or date range is supported ([QUERY.md](QUERY.md)).
- **A connected source is copied, not queried in place.** A read-only PostgreSQL or MySQL connection pulls the table into a new dataset version (a confirmation is tied to one version of the data, so it has to be a copy); one pull is capped at 500,000 rows and about 200 MB, and only these two databases are supported. The data changes only at the next pull (by hand or on a schedule).
- **The skill pack is a snapshot.** The skill pack downloaded from the AI tool access page (AI 工具接入) is a copy of the confirmed definitions at that moment; if the data changes or a definition goes back for another look afterwards, it does not know and does not refuse. For answers that follow the current data, connect over MCP.
- **Questions we need is new.** It has been checked with a scripted model in tests and once with a real model on the demo data, on the build before the verdicts were corrected (2026-11-22, 9 questions asked 5 times each). A run goes on in the service after it starts; if the service stops, the run is closed as stopped on the next request and the calls it made are charged. A run asks as the person who runs it, so it is open only to a builder or an admin whom no type list, column rule or row rule limits; a row rule limits every builder it does not give all rows, so where a type has row rules only an admin, or a builder those rules give all rows, can run it; a limited builder does not see the list. The comparison is exact (16 and 16.0 match, 1,234.57 and 1,234.5678 do not) and only one number per question: a list of groups or a share cannot be an expectation yet, and the expectation records the number, not how it was worked out (a count and a sum that happen to be equal both pass). An expected refusal passes only on a refusal the gate made (a definition not confirmed or waiting, nothing in scope, a relation that cannot be followed, a query that left out a confirmed definition, a measure waiting for confirming), and only when it names the expected definition if one is given; anything else with no number is "no answer". "Needs another look" is decided only when an answer is wrong, and only on what the expected answer read; when nothing is recorded yet (confirmed before any run gave the expected answer), a wrong answer is a failure until a run passes. A result is shown with its verdict only while the question stands as it was judged; after its words or expectation change, or it is confirmed again, it shows only what was answered then, until the next run. One service per workspace file: a second service process on the same file would take the first one's run as cut off, close it and could start another beside it. An edit of a definition's wording alone sends it back; once it is confirmed again (at a new version) that counts as a move of what the expected answer read, so one later wrong number shows as "needs another look" instead of "differs"; the run after that judges it plainly. A blocker written by name must name one definition when it is written; a definition given the same name later would also satisfy it, so write the id when names may repeat. The sentences a run stored (a refusal's reason) are in the language of the person who ran it. Runs are not scheduled, and the list cannot be exported.
- **Lists and lookups are narrow.** A question or a query can list the objects of one object type under conditions on that type (no condition across a relation, no OR, no text matching, no sort but the key), at most 50 a page, or find one object by its whole key, compared as stored (case counts; a number in its plain form). A lookup shows the type's properties and its confirmed per-row formulas, not statistics through relations. A lookup applies a view the question names (on its own type's table only), never a meaning: a lookup asked with a meaning is refused. The only relative date is `today`, the bare word on a date property, the date in the service's time zone when the query runs: a quoted `'today'`, `"Today "` or a parameter given `today` is text and refused as before, and there is no yesterday, this week or last month. A view can compare a confirmed per-row derived property (a function giving a number or yes/no) with a number, and nothing else of a derived property. A list reads every row the asker may read, as a count does; a lookup reads only the rows that have the key, but the datasets have no index on the key, so the database looks through the table to find them. Tried with a scripted model only; a real model writing lists and lookups, and the page's list table in a browser, are not checked yet. A list or a lookup on a pipeline's output shows each row as stored, a figure a join repeated included (an order's amount on each of its lines), and says nothing about the repeat; adding that figure up is still refused, with or without a list beside it. Boards show numbers only.
- **Two builders who both changed a definition need a third person or an undo.** Nobody who changed a definition since it was last confirmed may confirm it, whatever they changed (a name, a description, an other name), and any change to a confirmed one sends it back, its last confirmer's included. So in a team of two builders, once both have changed it, neither can confirm it: a third builder confirms it (an admin can give another person the builder role), or one of them puts it back exactly as it was last confirmed, which confirms it again by itself only if nothing it reads, directly or through what those read, moved meanwhile (a new data version, a change, a move to needs another look, a new confirmation; even a pipeline's new description upstream): otherwise a person looks again. Whoever is held is told who changed it and these ways out (for a pipeline, only the first: it has no undo). A save that leaves the description out keeps the stored one and is no change. Putting a definition back does not bring back what its change sent back with it (the relations, views and properties that read it need confirming again). Who changed it is kept with each definition; a file written by an older version keeps no such record, and then everyone the log names as having changed it since it was last confirmed is held, with its proposer. A pipeline follows its own rule for changed steps, and a new description now counts as one: editing only a confirmed pipeline's description sends it back for a second person, stops its scheduled runs and sends the definitions on its output datasets to "needs another look" (questions on them are refused) until it and they are confirmed again; putting the words back is another change, not an undo. A question we need's source (its note) is not part of what is confirmed: changing it alone keeps the expectation confirmed.
- **The page has been used on macOS only.** Backend and page unit tests pass on Linux (CI); Windows is untested.
- **Answers from documents are narrow.** A passage is at most 600 characters (a long paragraph is cut at sentence ends) and at most 5 passages go to the model per question; a document holds at most 200,000 characters (the file itself at most 10 MB) and a workspace at most 50 documents. Search is literal matching on SQLite FTS5 (pairs of Chinese characters and English words, any one of them, ranked by bm25), with no vectors, so a synonym or a question in other words does not find its passage; a common word (such as "orders") also sends passages with a data question, which does not change its answer but sends the model a few more passages. An answer is the documents' own words as the assistant picks them: which sentences it quotes, and whether it left a relevant one out, is the assistant's choice; code checks only that each quote is word for word (full-width and half-width punctuation or spacing that differ do not match, and the answer is refused), has at least 4 letters or decimal digits (0 to 9 in any script, full-width and Arabic-Indic digits included; ½, ① or Ⅳ do not count), and neither repeats nor overlaps another quote. Each quote is shown in the whole sentence that holds it (a sentence ends only at 。！？!?; a semicolon does not end one, so "…but … excepted" after it stays in the sentence; an English full stop does not end one either, so English sentences show as one longer run), the quoted part marked, so a negation or an exception cut off from it is still in sight. Whether the quoted words answer the question is for the person reading them to judge. When the model read passages and answered nothing from them, only the service's sentence "The assistant did not answer from the passages it was given" is shown; when it wrote a query the engine cannot run, only the service's sentence for that case; neither the model's reasoning nor its query is shown or kept. Without passages, this is as before. The explanation under a data answer, and under a "definition not met" refusal, is the model's own and may mention passages it was sent. With a passage sent, a data question whose query cannot run gets this generic sentence instead of the engine's specific cause (an unknown property, type or function). Documents answer only in the default Q&A (the model writes a structured query); when the model writes OntoPoc Query (writes=query) documents are not read. A builder can send a confirmed document back (with a reason; it leaves search at once and waits for a second person to confirm it again) or remove it (with a reason; its passages and index entries go, the log keeps who, when and why, answers that quoted it reopen refused, and a file of the same name may be uploaded again as a new document). A builder's token may send a document back (the log names the token); removing is done only by a person signed in to the page, never by a token. A removed document cannot be restored, only uploaded again, and a whole document is sent back, never one passage. Builders only is set at upload, and changing it means uploading again (a new version, confirmed again). A viewer does not see documents waiting for confirmation, so their refusals never mention one. Without FTS5 in the machine's SQLite the feature is off. A question still passes the old gate first: one that names an unconfirmed definition, or one asked with no confirmed object type in the asker's scope, is refused before the model is asked, so no document is used either. Tried only with a scripted model and made-up contracts and rules, not with a real model or real customer documents.
- **A kept answer keeps the language it was asked in.** A document answer asked in English and reopened on a Chinese page still reads in English ("These are the documents' own words … paragraph 3"), as kept reasons do on main.
- **An older OntoPoc cannot reopen kept document answers.** A version without answers from documents fails when it reopens an answer that quoted a document (it cannot read a `document:` definition); after going back to an older version, read those answers in the newer one.
- **The public demo image has no pdftotext.** A PDF uploaded on the demo is refused with the sentence that pdftotext is needed; .md, .txt and .docx work. The image is not changing for now.
