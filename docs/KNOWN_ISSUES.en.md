# Known issues

Moved from the [README](../README.en.md). Issues that belong only to the earlier screen (`legacy.html`) are in [LEGACY_SCREEN.en.md](LEGACY_SCREEN.en.md#known-issues).

- **Questions about a relation between objects of the same kind have no direction yet.** Relations such as employee reports-to or parent-child organisation can be modelled, verified and exported; but a question cannot say superior or subordinate, so it states the limit and stops.
- **The relation check only requires one connected row.** In the data check, a relation passes as soon as it connects one row, even if the share of rows that connect is very low; the page states how many rows connect, so look at that number.
- **Definitions and joins are narrow.** A code meaning covers a few values of one column; a repeated number has three ways to be read; a join has only input, join and output steps and refuses to run past a row cap; the name-versus-calculation check knows only P50, P90, mean, total, max and min, and needs a same-named source column in another table. All of this has been tried only on synthetic planted tables and public data, never on a real client's data.
- **Value rules are narrow.** A rule is on one object type only (never across types), on a property of its own dataset (not on a derived property), and is one of a fixed few: not empty, a comparison with a number or a range of numbers, one of the codes with a meaning, one date not before another of the same type. Comparisons are with numbers only, not with a fixed date; no formula, no rule engine, at most 20 rules per type. Rules are not yet exported as SHACL. Measured on 150,000 rows with 10 rules on one Mac: the rule pass takes about 0.8 s, run before a recheck or a group confirmation takes the write lock; tried on synthetic data only. The count of items to confirm, the type list and the review queue list do not count rules on every page: they use the count kept by the type's last proposal, confirmation or recheck, so a waiting type whose data got a new version is left out of the count until someone opens it (opening it keeps the count it makes). Counting reads the rows without a write lock, but the workspace file uses SQLite's rollback journal, so while a count runs another writer's commit waits for it (as long as the count takes: 0.3 to 0.8 s measured on 150,000 rows with 10 rules, on the type page, a proposal or a confirmation; moving to SQLite's write-ahead log would end this and is not done).
- **An older version of OntoPoc on a file with value rules ignores them.** Run on such a file, a version without value rules opens it, keeps the rules through an edit of a type's name or description, drops them on an edit of its key or properties (the type then waits for confirmation again), does not count them on an upload, and lets a person confirm a type whatever its rules say. This version trusts a confirmed type's rules only when the latest count it kept was made on the type's current data, for its current rules and codes, and shows no broken row. Until that holds, every page and readout that shows or uses the type (the type list, the explorer, boards, questions, the agent's readouts, the OWL and SHACL download) shows it as needing another look and does not use it. Deciding this counts nothing; a board or an explorer page opened by a builder still counts the rules of a type that waits, each time, to show how many rows break each. The count is made once the service has started (after the port is open), when someone opens the type, and before the first question or agent readout that would use it: a type with no usable count is counted, and one with a broken rule is sent back, telling the people who can confirm it once. A count that fails sends the type back saying its rules could not be checked; the service and other requests carry on.
- **The "Counts repeated rows" mark does not reach everywhere.** It looks only at joins inside pipelines: a table uploaded already joined, or joined elsewhere and pulled in, carries no mark and can still add up too high. Across pipelines the mark does not come off: a later pipeline that dedupes on the order key is still refused (it has none of the earlier join's row columns), so it may refuse more than it needs to. Two right numbers are refused too: the max amount grouped by customer and the average amount grouped by order stay marked, so a sum over those tables is refused (what cannot be proved stays). A column the aggregate groups by alone carries no mark (each value is on one row). A "latest" statistic and a one-to-one lookup still answer: copies do not change them. After an upgrade, each pipeline output with a join written by an earlier version answers only once its pipeline has run again (see the README); until then its checked numbers show as refused rather than "needs another look" (a checked number has no such state), and its questions we need go back to "needs another look".
- **One service process per workspace file.** Counting and judging value rules is done one at a time within one process; two processes on the same file may each count the same type.
- **Answer checks rely on the model declaring honestly.** Code checks that the query that ran matches how the model said it read the question; if the model misstates the reading and the query happens to match, the check cannot see it. The query language can say "equals a value", "is none of these values", numeric and date ranges (see [QUERY.md](QUERY.md)), and the top or bottom N.
- **The same plain question can be read two ways.** For "What is sales?" the model may count every row or only a confirmed view, so the main number can differ between two asks; both numbers are shown when the model answers on all rows or includes the view by name; when it writes the view's conditions out itself, only its number is shown.
- **Other names are heard only as written.** A name or other name with Chinese in it is found anywhere in a question, one in letters only as a whole word (an English name also in its plural or singular); other names ignore case and full or half width. A misspelling, or a synonym nobody wrote down as an other name, is not heard, and then the model's reading decides. An other name found only inside a longer name of another definition is not heard there (on the demo, Customer's other name 客户 inside the property's 客户号).
- **A definition's own name is heard even inside a longer name, as before.** Where the short one is a name, not an other name, it is never muted: the pilot's type 客户 inside a property's other name 客户号 is heard, so "客户号C015的订单有几笔？" is refused while that type waits, as main refuses a name inside a longer name. A short name can still be heard inside a word that is no name of anything: that only ever refuses, never changes a number. OntoPoc Query does not take other names: it names types and relations by their name or English name.
- **A question that names a view the model does not read is refused, even when the model's own filter is right.** "Amount of the orders that are not valid orders" with the model leaving out Paid, Shipped and Delivered is refused because the question names Valid orders (by its name or an other name) and the query does not read it; so is a question naming the view and a meaning together, answered by grouping. The refusal says why; ask without the view's name.
- **A condition the model leaves out is not caught.** When the question asks for part of the rows and the model writes no condition, the answer covers every row.
- **"Lowest" ranks only groups that have rows.** "The customer with the lowest order total" ranks customers that have orders; a customer who never ordered is not among them.
- **A real model's answers vary.** Asked the same question several times, it now and then writes a query code refuses (a refusal, not a wrong number). Each round ends with `scripts/real_model_check.py`, which checks answers on the bundled data against SQL.
- **"Needs another look" is judged by share of the table.** A value's rows must more than double or fall below half, and by at least 5 rows. These two numbers are chosen, not measured; a shift smaller than that goes unnoticed.
- **Code finds only some missing relations.** Removing each relation in turn on 17 saved runs (public and synthetic data), it found 24 of 33 again; on complete ontologies it has not suggested a false one.
- **Queries cannot yet** work out two different numbers in one question (a total and an average, say), or say which things tend to appear together. It says so when asked. Filtering by a numeric or date range is supported ([QUERY.md](QUERY.md)).
- **A connected source is copied, not queried in place.** A read-only PostgreSQL or MySQL connection pulls the table into a new dataset version (a confirmation is tied to one version of the data, so it has to be a copy); one pull is capped at 500,000 rows and about 200 MB, and only these two databases are supported. The data changes only at the next pull (by hand or on a schedule).
- **The skill pack is a snapshot.** The skill pack downloaded from the AI tool access page (AI 工具接入) is a copy of the confirmed definitions at that moment; if the data changes or a definition goes back for another look afterwards, it does not know and does not refuse. For answers that follow the current data, connect over MCP.
- **Questions we need is new.** It has been checked with a scripted model in tests and once with a real model on the demo data, on the build before the verdicts were corrected (2026-11-22, 9 questions asked 5 times each). A run goes on in the service after it starts; if the service stops, the run is closed as stopped on the next request and the calls it made are charged. A run asks as the person who runs it, so it is open only to a builder or an admin whom no type list, column rule or row rule limits; a row rule limits every builder it does not give all rows, so where a type has row rules only an admin, or a builder those rules give all rows, can run it; a limited builder does not see the list. The comparison is exact (16 and 16.0 match, 1,234.57 and 1,234.5678 do not) and only one number per question: a list of groups or a share cannot be an expectation yet, and the expectation records the number, not how it was worked out (a count and a sum that happen to be equal both pass). An expected refusal passes only on a refusal the gate made (a definition not confirmed or waiting, nothing in scope, a relation that cannot be followed, a query that left out a confirmed definition, a measure waiting for confirming), and only when it names the expected definition if one is given; anything else with no number is "no answer". "Needs another look" is decided only when an answer is wrong, and only on what the expected answer read; when nothing is recorded yet (confirmed before any run gave the expected answer), a wrong answer is a failure until a run passes. A result is shown with its verdict only while the question stands as it was judged; after its words or expectation change, or it is confirmed again, it shows only what was answered then, until the next run. One service per workspace file: a second service process on the same file would take the first one's run as cut off, close it and could start another beside it. An edit of a definition's wording alone (it stays confirmed, at a new version) counts as a move of what the expected answer read, so one later wrong number shows as "needs another look" instead of "differs"; the run after that judges it plainly. A blocker written by name must name one definition when it is written; a definition given the same name later would also satisfy it, so write the id when names may repeat. The sentences a run stored (a refusal's reason) are in the language of the person who ran it. Runs are not scheduled, and the list cannot be exported.
- **The page has been used on macOS only.** Backend and page unit tests pass on Linux (CI); Windows is untested.
