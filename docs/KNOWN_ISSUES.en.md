# Known issues

Moved from the [README](../README.en.md). Issues that belong only to the earlier screen (`legacy.html`) are in [LEGACY_SCREEN.en.md](LEGACY_SCREEN.en.md#known-issues).

- **Questions about a relation between objects of the same kind have no direction yet.** Relations such as employee reports-to or parent-child organisation can be modelled, verified and exported; but a question cannot say superior or subordinate, so it states the limit and stops.
- **The relation check only requires one connected row.** In the data check, a relation passes as soon as it connects one row, even if the share of rows that connect is very low; the page states how many rows connect, so look at that number.
- **Definitions and joins are narrow.** A code meaning covers a few values of one column; a repeated number has three ways to be read; a join has only input, join and output steps and refuses to run past a row cap; the name-versus-calculation check knows only P50, P90, mean, total, max and min, and needs a same-named source column in another table. All of this has been tried only on synthetic planted tables and public data, never on a real client's data.
- **Value rules are narrow.** A rule is on one object type only (never across types), on a property of its own dataset (not on a derived property), and is one of a fixed few: not empty, a comparison with a number or a range of numbers, one of the codes with a meaning, one date not before another of the same type. Comparisons are with numbers only, not with a fixed date; no formula, no rule engine, at most 20 rules per type. Rules are not yet exported as SHACL. Measured on 150,000 rows with 10 rules on one Mac: the rule pass takes about 0.8 s, run before a recheck or a group confirmation takes the write lock; tried on synthetic data only. The count of items to confirm, the type list and the review queue list do not count rules on every page: they use the count kept by the type's last proposal, confirmation or recheck, so a waiting type whose data got a new version is left out of the count until someone opens it (opening it keeps the count it makes). Counting reads the rows without a write lock, but the workspace file uses SQLite's rollback journal, so while a count runs another writer's commit waits for it (as long as the count takes: 0.3 to 0.8 s measured on 150,000 rows with 10 rules, on the type page, a proposal or a confirmation; moving to SQLite's write-ahead log would end this and is not done).
- **An older version of OntoPoc on a file with value rules ignores them.** Run on such a file, a version without value rules opens it, keeps the rules through an edit of a type's name or description, drops them on an edit of its key or properties (the type then waits for confirmation again), and does not count them on an upload, so a type stays confirmed on data that breaks a rule. Back on this version, the service counts the rules of every confirmed type that has no count on its current data when it starts, and before the first question or readout that would use the type, and sends back any type whose rule is broken; the people who can confirm it are told once.
- **Answer checks rely on the model declaring honestly.** Code checks that the query that ran matches how the model said it read the question; if the model misstates the reading and the query happens to match, the check cannot see it. The query language can say "equals a value", "is none of these values", numeric and date ranges (see [QUERY.md](QUERY.md)), and the top or bottom N.
- **The same plain question can be read two ways.** For "What is sales?" the model may count every row or only a confirmed view, so the main number can differ between two asks; both numbers are shown when the model answers on all rows or includes the view by name; when it writes the view's conditions out itself, only its number is shown.
- **A condition the model leaves out is not caught.** When the question asks for part of the rows and the model writes no condition, the answer covers every row.
- **"Lowest" ranks only groups that have rows.** "The customer with the lowest order total" ranks customers that have orders; a customer who never ordered is not among them.
- **A real model's answers vary.** Asked the same question several times, it now and then writes a query code refuses (a refusal, not a wrong number). Each round ends with `scripts/real_model_check.py`, which checks answers on the bundled data against SQL.
- **"Needs another look" is judged by share of the table.** A value's rows must more than double or fall below half, and by at least 5 rows. These two numbers are chosen, not measured; a shift smaller than that goes unnoticed.
- **Code finds only some missing relations.** Removing each relation in turn on 17 saved runs (public and synthetic data), it found 24 of 33 again; on complete ontologies it has not suggested a false one.
- **Queries cannot yet** work out two different numbers in one question (a total and an average, say), or say which things tend to appear together. It says so when asked. Filtering by a numeric or date range is supported ([QUERY.md](QUERY.md)).
- **A connected source is copied, not queried in place.** A read-only PostgreSQL or MySQL connection pulls the table into a new dataset version (a confirmation is tied to one version of the data, so it has to be a copy); one pull is capped at 500,000 rows and about 200 MB, and only these two databases are supported. The data changes only at the next pull (by hand or on a schedule).
- **The skill pack is a snapshot.** The skill pack downloaded from the AI tool access page (AI 工具接入) is a copy of the confirmed definitions at that moment; if the data changes or a definition goes back for another look afterwards, it does not know and does not refuse. For answers that follow the current data, connect over MCP.
- **The page has been used on macOS only.** Backend and page unit tests pass on Linux (CI); Windows is untested.
