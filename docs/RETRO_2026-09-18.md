# 复盘 · 2026-09-18

写给二十天后再打开这个仓库的人（多半是作者自己）。数字都是今天从仓库里数出来的。

## 1. 走到哪了

2026-08-29 起步，到今天 20 天，30 个 PR、415 个提交，其中 243 个是 9-14 定下现方向之后的四天半里写的。后端约 3600 行、页面约 4000 行，测试后端 365、页面 133，每个 PR 都跑。

现在这个东西能做的事：上传几张业务表或一份文档 → 模型起草本体、代码拿每一行核验 → 六项数据体检 → 模型出业务问题、代码算答案（计数、占比、求和、平均、多维分组）→ 同一份文件建三次标出拿不准的地方 → 人逐项确认、采纳名称对应、固定 1 到 3 道验收问题 → 存成这份文件的参考本体，下次上传自动对照并预填。

**没发生过的事只有一件，也是最要紧的一件：没有任何一个作者以外的人用过它。** 结算线 2026-11-29。

## 2. 方向换了五次，换对了什么

售前方案编译器 → 供应链 → 合成质量演示 → 食品召回 → 召回范围研判 → 上传建本体。前四次换的是行业场景，最后一次换的是产品形状：从"替某个行业做一件事"变成"替实施顾问做一件到哪都要做的事"。这一次换对了，证据是后面四天半的功能都长在同一根主干上，没有再推倒。

代价也是真的：README 直到昨天还有三分之一篇幅在讲召回的命令行，代码位置表列的全是上一个方向的文件。方向换得快，对外的说法跟不上，读的人分不清这是本体工具还是召回审查工具。昨天才改。

## 3. 哪些做法被证明值钱

- **模型提议、代码核验、人决定。** 不是口号：v5 的 24 道真题里 23 道答出，每个数字都和 Python 逐行算的对得上；模型漏掉的、说错的，代码都能指出是哪一行。这条分工是整个项目里唯一没动摇过的东西。
- **先写失败测试、单独提交。** 昨天这一轮，两次改动碰坏了已有的页面测试，都是在提交前被拦下的。全局的提交检查会挡住"测试和代码一起改"的提交，挡了一次，挡得对。
- **只用公开数据，但要用真的。** 合成的示例公司从来没逼出过问题。芝加哥合同逼出了日期正则不认时间戳（整份数据建不起来）；英国零售逼出了一次返回 5 MB 撑爆浏览器；CMS 医院数据逼出了属性列同义写法这个窟窿。每份真数据至少值一个 bug。
- **多视角评审之后，主线程逐条回代码核实。** 评审说的话大约三成是错的或半对的（例如"多表建模不稳"，实测 17 次全过）。不核实就焊进计划，计划就是歪的。

## 4. 哪些地方反复栽

- **改了后端忘记重启本机服务。** 文档里写了、记忆里写了，昨天还是又犯了一次，核验看到的是旧代码的行为。它没有代码层面的拦截，只有页面上一句"服务是旧版本"的提示。靠自觉的规矩守不住，这是今天为止唯一一条这样的规矩。
- **提交前不看测试输出。** 这一程里发生过两次，把失败的测试一起提交了。现在的做法是改、测、提交分三步走，不写在一条命令里。
- **把自己脚本的输出读反了。** `changed: False` 被读成"有差异"。数字要先看字段的定义再下结论。
- **子任务会无声地死。** 昨天七个后台评审里五个死于网络或流中断。现在的做法是它们的活主线程都能接，不把结论押在某一个上。

## 5. 最不舒服的一条

昨天让人专门唱反调，它说的最重的一句是：**这个项目已经第六次"自己挑数据、自己证明通过"了。** 迭代 6 原定的"试用轮"仍然是作者自己跑自己的工具，而结算线认的是"被真实用过一次"——自己跑不算，算的话 306 道问答早就够了。

这条站得住。所以迭代 6 改了：CMS 压成一天的冒烟，省下的时间用来找一个不是作者的人，全程不插手地用一遍。

它还有一条站不太住但值得留着的怀疑：这工具省的可能只是有经验的顾问 30 到 60 分钟的画图时间。反驳是省的不是画的时间，是"画完说不清哪里和数据对不上"的那一段。这个反驳现在没有证据，只有一个真人用过之后才会有。
