# 迭代 9：闭环

## 目标

OntoPoc 现在的每一块都能用，但它们各自为政：问答答不了就停在"答不了"，确认完不知道新版本有没有变差，Agent 查本体要翻全部。这一轮把它们接成一个闭环，每一步的产出是下一步的输入，人在关键处拍板。

```
上传 ─▶ 建模（模型提出、代码核验）─▶ 人确认
                                        │
        ┌───────────────────────────────┘
        ▼
      问答（只用确认过的）── 答不了 ─▶ 说清缺哪块，当场补：
        │                              派生指标 / 口径 / 关系
        │                              （模型提出、代码核算、人确认）
        ▼                                         │
   固定为验收问题 ◀──────────────────────────────┘
        │
        ▼
  新版本或重传 ─▶ 发布闸门：验收问题新旧对比，退步要人点头
        │
        ▼
  对外：页面、导出、插件、Agent 按需查询
        │
        ▼
  记下答不了的问题、Agent 查不到的概念 ─▶ 改进建议（人批准）─▶ 回到确认
```

原则不变：模型只提议，代码核算，人决定；每次操作串联调用模型至多 3 步；不编阈值；数据留在本机。

## 轮次

每轮先交失败测试，再实现；每轮一个 PR；真实模型端到端跑一次再交。

### 第 1 轮：派生指标，答不了说人话

- 对象可以有**派生指标**，例如"订单明细.金额 = 数量 × 单价 ×（1 − 折扣）"。公式只允许：几个字段相乘、乘"1 − 某字段"、两项相加减。不允许任意表达式。
- 出题员遇到需要派生才能答的问题，提出公式；代码在每一行上算一遍，报出算出几行、跳过几行和原因；人确认后存下（跟着文件走，和规则、表单一样）。确认之后，问答可以对它求和、求平均。
- "答不了"改成一句中文原因，英文内部名换成中文名，模型原文收进可展开的详情。
- 验收：Northwind"每个客户买了多少钱"，确认一次派生指标后答出来，数字由测试独立算一遍对上。

### 第 2 轮：口径

- 对象和字段可以挂**口径**：类型（取值含义、单位、适用范围、业务规则、数据质量）、会不会导致结果错、触发词。
- 问题里出现触发词，出题员能看到对应口径；答案下面列出"这个答案用了哪些口径"。
- 口径来源：人写，或模型从文档里提出、原文核对后由人确认。

### 第 3 轮：问答界面重做成闭环

- 一道题的完整过程在一处看完：问题 → 查询路径（在图上）→ 答案 → 用到的对象、关系、口径和数据行数 → 答不了时缺哪块 → "补上这一项"的入口 → 存为验收问题。
- 补上之后原题自动重算，前后对照。

### 第 4 轮：版本与发布闸门

- 每次确认生成一个带编号的**已确认版本**，旧版本只读、可对照、可退回。
- "和上次比"细到字段：新增、删除、改名、识别方式变化。
- 新版本顶替已确认版本之前，验收问题新旧各算一遍：有题从能答变成答不了、或数字变了，就列出来，人点头才发布。

### 第 5 轮：Agent 按需查询

- MCP 增加一份精简清单（版本、各类数量、怎么查）和两个查询工具：按需求找概念、把概念解析到表、字段、关系、口径和依据。
- 有上限，不给全量目录，查不到明说。按中文可用的方式匹配（不按空格切词）。
- 只给已确认版本。

### 第 6 轮：使用记录与改进建议

- 记下问答里答不了的问题（及原因）、Agent 查询里查不到的概念。
- 攒到有东西可说时，出一份改进建议：补哪个派生指标、加哪条口径、缺哪个对象。每条带证据（哪些问题因此答不了）。模型提议，人批准，批准后走第 4 轮的闸门，不自动发布。

## 不做

- 自动演化、自动发布：裁判是人。
- 任意表达式、自由写 SQL。
- Codex 插件：等有人要再做。
