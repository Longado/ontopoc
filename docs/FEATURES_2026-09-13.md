# OntoPoc 功能清单 · 2026-09-13 归档

> 归档点：分支 `codex/recall-scope-deepseek`，标签 `archive-2026-09-13-nhtsa-review`。未合并 main、未部署。本文只列代码里实际存在、并在 2026-09-13 跑过验证的功能；没做的写在第 4 节。

## 1. 一句话

给一份公开的汽车召回与车主投诉数据，系统自动搭建本体、用代码核验，算出每个召回范围内外的同类投诉，让模型读投诉原文给初判，再由质量工程师在页面上逐条复核；复核结果就是校准模型的标注。

场景：美国 NHTSA 公开数据，雪佛兰 Bolt EV / EUV 2017–2023，13 个召回、679 条车主投诉，2026-09-13 取数。

## 2. 质量工程师在页面上能做什么

布局：左侧导航（召回范围研判、事件 95876 核对、产品首页），主区是页头（标题、本体确认状态、数据说明）加四个标签页，内容用卡片分区；分区方式参考 EIP（nano-ontoprompt），配色和 Logo 用 OntoPoc 自己的。

入口：`npm --prefix landing-page run dev` 后打开首页，默认场景"汽车召回范围研判（NHTSA）"。页面只读静态数据，不需要本机 Python 服务。

| 步 | 能做的事 |
|---|---|
| ① 看并确认本体 | 看系统搭建的 4 类核心对象（召回、车型年款、部件、投诉）及其关系、每类对象取自哪些字段、时间字段、过滤条件、两个来源的名称对应（附多连上的记录数和理由）、被代码拒绝的对应、模型指出的数据缺口、未使用的字段。确认后才能复核 |
| ② 选召回 | 13 个召回按部件分成 6 组、组内按日期排；原文写明"修复后再召回"的连成系列（电池 5 次、车顶 2 次），标出接续关系；每个召回显示覆盖的车型年款、范围外投诉数、是否已有模型初判 |
| ③ 复核候选投诉 | 按"本召回范围内 / 其他同类召回已覆盖 / 所有同类召回之外"三类看；列表按召回后 → 起火或碰撞 → 提交日期排序，每条标"召回后 N 天 / 起火 / 碰撞 / 经名称对应"；详情显示投诉原文（模型引用的证据高亮）、投诉部件、召回与投诉日期、被哪次召回覆盖、模型初判与理由；标"同一缺陷 / 不是 / 说不清"，点选即存，可加备注，同一系列共用结论 |
| ④ 看结果、下载 | 显示人工与模型一致的条数和分歧条目（可点回去看）；下载复核结果（JSON，含模型判断和提示词版本）；页面同时说明有多少投诉没进入任何召回的候选、部件最多的是什么 |

复核记录存在本机浏览器，刷新可恢复；本机记录损坏时不覆盖原记录。页面在手机宽度下可用（列表与详情上下排列，点选后跳到详情，可返回列表）。

## 3. 系统背后做了什么

| 能力 | 做法 | 谁判断 |
|---|---|---|
| 公开数据快照 | `scripts/fetch_nhtsa_snapshot.py` 按品牌、车型、年款取数；记录每个请求的地址和时间；召回按活动号+车型+年款去重、投诉按编号去重；两个来源的日期格式不同（召回日/月/年、投诉月/日/年），按来源解析成统一日期，任一值解析失败即拒绝 | 代码 |
| 自动搭建本体 | 模型只看字段名和示例值，提出对象类型、身份字段、属性、关系、时间字段、过滤条件、忽略字段、数据缺口；提示词 `public_ontology_modeler.v3` | 模型（1 次） |
| 本体核验 | 17 种错误码，例如字段不存在、同一对象在两个来源的身份键不同、字段没用上也没写忽略理由、四个角色不齐、关系在数据里零连接、两个来源没有共享对象、时间字段不是日期、过滤条件无效。有错就回传模型重做，没有进展或满 3 次就停，标为不可用 | 代码 |
| 跨来源名称对应 | 把只出现在一个来源的名称交给模型提出对应（提示词 `public_value_alias.v1`）；代码逐条核验名称存在、原本没连上、不重复、确实多连上记录，否则拒绝并写明原因。本次接受 1 条：投诉"SERVICE BRAKES"对应召回"SERVICE BRAKES, HYDRAULIC"，多连上 34 条 | 模型提出，代码核验，人确认 |
| 范围查询 | 给定一个召回，算覆盖的车型年款、同部件（含上级类别）的投诉，分三类；每条标召回前后与间隔天数、是否经名称对应、被哪些同部件召回覆盖 | 代码 |
| 投诉原文判断 | 每 20 条一批，输入召回描述、召回部件、投诉部件和原文；判"同一缺陷 / 不是 / 说不清"，判"同一缺陷"必须引用原文片段，代码核对片段真在原文里，否则降为"说不清"；temperature 0；提示词 `public_defect_match.v3` | 模型（每批 1 次） |
| 数据版本锚定 | 本体记录它所用数据的哈希；范围查询、原文判断、打包页面数据前都核对，不一致就拒绝 | 代码 |
| 页面数据打包 | `scripts/build_public_review_pack.py` 从在线运行报告和快照生成页面数据，重算全部召回的范围并与报告比对，不一致就拒绝；`--check` 验证页面数据未过时 | 代码 |
| 在线运行 | `scripts/run_public_ontology.py --campaign ...`：读本机 DeepSeek 凭据（不打印、不入库），依次搭本体、名称对应、逐个召回查范围和判断原文，每步写报告，拒绝覆盖已有报告 | — |

## 4. 验证过的结果与边界

2026-09-13 在线运行（`examples/nhtsa/runs/2026-09-13-deepseek-flash-v4.json`，快照已去掉 NHTSA 测试占位行）：

- 本体第 2 次提交通过核验（第 1 次漏写 2 个字段的去向，被代码退回）。
- 电池召回 21V650000：287 条候选，范围外 43 条全部在召回之后；24V812000 的范围外为召回前 21 条、召回后 22 条。
- 两个刹车召回：从 0 条候选变为各 34 条，全部经名称对应。
- 13 个召回全部有模型初判（每个系列跑一次，系列内共用）。
- 回归：后端 105 项、前端 29 项、Sites 4 项；浏览器桌面真实点击走完四步。

边界（没做或做不到的）：

- 范围只到车型年款，召回数据没有车架号。
- 模型原文判断不稳定，只能当初判：同一提示词（v2）两次运行，电池 287 条中 261 条相同；2023 款座椅下起火投诉 11600123 两个版本都判"不是"。还没有人工标注的回归样本。
- 名称对应只补上了刹车；"燃油/动力系统"60 条投诉模型没有对到电池，仍在盲区统计里。NHTSA 的 3 条测试占位行已在取数时去掉（规则记录在快照 `cleaning` 字段）。
- 页面只有中文；本体卡片里仍显示原始字段路径（投诉详情里的字段已是中文名）。
- 四个角色（事件、受影响对象、部件机制、信号）是为"召回 × 投诉范围研判"设计的，不是任意问题的本体平台；单一来源的数据写不出能通过核验的本体。
- 复核是本机记录，不是审批，也不代表缺陷已确认、车辆已召回或已处置。
