# OntoPoc 里的 Agent

这里的 Agent 是**一次有边界的模型判断，加上代码对它的核验**。它不调用别的 Agent，不决定下一步做什么；谁先谁后由代码写死。这是护栏"模型只做一次判断、代码做所有循环""不做多 Agent 编排"两条的具体样子。

产品里一共五个。每次模型调用都从 `src/ontology_poc_generator/agent_harness.py` 的 `ask_model` 这一个入口出去，用这里的名字登记，否则发不出去。

## 四张定义卡

### 表格建模员（`table_modeller`）

| | |
|---|---|
| 判断什么 | 这些字段描述哪些业务对象、各自靠什么识别、彼此怎么连 |
| 什么时候叫它 | 上传表格后自动。一次上传里它被独立叫三次（一次正式、两次用来比稳定性），每次内部最多改三版 |
| 给它看什么 | 每列的字段名、每列最多 3 个示例值（截到 140 字）、建模目的；改版时再加上一版和代码找到的错误。**不给看**：整行数据 |
| 它交出什么 | 对象、识别字段、属性、关系、标为不用的字段、没想清的问题 |
| 代码怎么核它 | 17 类错误：字段真不真在、识别字段有没有值、关系在数据里连不连得上、同一行只提到一个对象的"自连关系"不算连上，等等（`public_ontology.py` 的 `validate_proposal`、`graph_checks`） |
| 错了怎样 | 把错误原样发回让它改；一个错误都没改好就停，改到第三版也停；**账户余额不足立刻停**，不白试 |
| 不许做 | 编造字段、表、取值；拿自由文本、金额、日期当识别字段 |
| 提示词 | `company_ontology_modeler.v2`（召回示例用同一套引擎、另一份提示词） |

### 文档建模员（`document_modeller`）

| | |
|---|---|
| 判断什么 | 一段文字里提到了哪些业务概念、概念之间有什么关系 |
| 什么时候叫它 | 上传文档后自动。每段一次，最多 12 段，段与段互不重试 |
| 给它看什么 | 这一段原文（不超过 6000 字）、建模目的、前面几段已经确认的概念名。**不给看**：其他段的原文 |
| 它交出什么 | 概念（名字、定义、原文引用）、关系（两端、含义、原文引用） |
| 代码怎么核它 | 引用必须能在这一段原文里逐字找到；关系两端必须是已经核实的概念 |
| 错了怎样 | 找不到引用的那一条剔除并列出；某一段请求失败就跳过；账户余额不足不再往下试 |
| 不许做 | 编造引用；把标题、章节名、泛泛的词当概念 |
| 提示词 | `company_document_modeler.v1` |

**已知最弱的一环**：代码只证明"这句话确实在原文里"，证明不了"这句话真的支持这个概念或关系"。

### 出题员（`question_writer`）

| | |
|---|---|
| 判断什么 | 一个经营者会问的业务问题，该写成哪条结构化查询；写不出就说清卡在本体还是查询格式 |
| 什么时候叫它 | 建模通过后自动出一组（6 道）；顾问自己问一道时再叫一次 |
| 给它看什么 | 建模目的、本体里的对象关系属性、取值不超过 12 种的字段的全部取值。**不给看**：数据行 |
| 它交出什么 | 每道题的思路、题目、查询（或答不了的原因） |
| 代码怎么核它 | 查询里的每个对象、关系、字段都要在本体里存在；**答案全部由代码在数据上算**，不采信模型给的任何数字 |
| 错了怎样 | 不重试；查询走不通就标"本体缺"或"问法不支持"，照实写原因 |
| 不许做 | 引用本体里没有的东西；替查询格式做它做不到的事（时间段、数值区间） |
| 提示词 | `company_questions.v5` |

### 名称对应员（`variant_matcher`）

| | |
|---|---|
| 判断什么 | 同一类对象的一组名字里，哪几种写法其实是同一个东西 |
| 什么时候叫它 | 只在顾问点"找出可能的对应"时，一次 |
| 给它看什么 | 只按一个字段识别、取值 2 到 200 个的对象，每个名字和它出现的行数。**不给看**：是哪些行、其他字段 |
| 它交出什么 | 一组组写法，每组一句理由 |
| 代码怎么核它 | 每个写法必须真在数据里；结果一律标"等人决定"，**从不自动合并** |
| 错了怎样 | 数据里没有的那组丢掉并说原因；不重试 |
| 不许做 | 把只是相关的、同一集团的不同实体配在一起；配"未知""其他"这类占位值（这条只写在提示词里，代码没拦，靠"人来决定"兜底） |
| 提示词 | `company_name_variants.v1` |

### 字段释义员（`field_describer`）

2026-09-18 加的第五个，按下面"什么时候加第五个"的四条过的：它是一次有边界的判断、结果由代码核验；卡点真实存在（DIP 表单的中文名、描述、展示字段必填，英文表头时顾问要逐个手写）；它所在的动作只有这一次模型调用；登记在 `AGENTS` 里。

| | |
|---|---|
| 判断什么 | 每个对象、每个字段的中文业务名和一句话描述，以及每个对象用哪个字段展示给人看 |
| 什么时候叫它 | 只在顾问在对象的属性页点"起草"时，一次 |
| 给它看什么 | 建模目的；每个对象的 key、名称、字段名、类型、长度、是否识别字段、每个字段最多 3 个示例值。**不给看**：整行数据 |
| 它交出什么 | 每个对象的中文名、描述、展示字段，和每个字段的中文名、描述 |
| 代码怎么核它 | 对象和字段必须是这份本体里的；展示字段必须是这个对象自己的字段；中文名和描述必须是短文字。不合格的剔除并写明原因 |
| 错了怎样 | 不重试；请求失败就照实报；起草的每一项标"模型"，人改过的去掉标记，再起草也不覆盖人写的 |
| 不许做 | 编造对象或字段；看不出含义时乱猜（提示词要求留空） |
| 提示词 | `company_field_descriptions.v1` |

## 调用记录

服务把每次模型调用追加一行到 `output/ontology-runs/model_calls.jsonl`：什么时候、哪个 Agent、提示词版本、哪个模型、用了多少毫秒、成功还是失败、失败原因前 200 字。只记这些，不记提示词和回答的全文（全文里有数据）。

用途：查某次上传到底调了几次模型、哪一步慢、换提示词版本之后失败率有没有变。

## 什么时候加第五个

全部满足才加：

1. 它是一次有边界的判断，结果由代码核验；它不决定调用谁。
2. 有一个真撞到的卡点，不是"以后可能用得上"。
3. 它所在的那个用户动作，模型调用加起来不超过三次。
4. 在 `AGENTS` 里登记名字，写一张上面这样的卡。

"对话入口"如果只是把顾问的问题交给出题员，不需要新 Agent；要让模型来猜该交给谁，那本身就是一次判断，按这四条单独过。

## 参照过、没有照搬的

调研过 Instructor、DSPy、pydantic-ai、Guardrails AI、BAML 五个开源外壳，以及 DeepSeek 的 DSH。都没有直接引入：它们的卖点是由库来管重试、依赖注入、多轮编排，正是护栏要留在代码里的东西；而且它们的重试都是固定次数，我们的"一个错误都没改好就停"更严。借了三个思路：一个入口统一调用（Instructor、pydantic-ai），每次调用留记录（pydantic-ai 的调用追踪），服务知道自己是不是在跑旧代码（DSH 的热更新想解决的同一个问题，我们只做检测、不自动重启，因为正在跑的建模在进程里，重启就断；作业进度写在 `output/ontology-runs/jobs/`，重启后页面会说清这次中断了，而不是一直转圈）。还没做的一个：改提示词后拿一批标注样本跑回归比对（BAML 的 test、DSPy 的 Evaluate）。

## 外部 agent 怎么接

通过 MCP 工具（见 `docs/MCP.md`）。MCP 工具是入口，不是第五个 Agent：它们调用本机服务的同一套接口，模型调用仍然只走上面四张卡。
