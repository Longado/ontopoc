# 公开场景跑通 + 自动搭建本体 · 方案与验证记录（2026-09-13）

> 用户 2026-09-13 定的方向：选一个公开场景，从材料一路跑到结论；系统要能自动搭建本体。
> 本文替代 `HANDOFF_2026-09-13.md` 第 6、7 节原定的"先修工作台界面"顺序。

## 1. 场景

美国 NHTSA 汽车召回与车主投诉，公开接口，不需要密钥。

- 召回：`https://api.nhtsa.gov/recalls/recallsByVehicle?make=&model=&modelYear=`，每条是一次召回活动 × 一个车型年款，含部件、原因、后果、补救。
- 投诉：`https://api.nhtsa.gov/complaints/complaintsByVehicle?make=&model=&modelYear=`，每条是一条车主投诉，含车型年款列表、部件、描述、是否起火等。

业务问题：一次召回发布后，哪些车型年款在范围内；哪些投诉指向同一部件；其中哪些车辆不在任何同部件召回的范围里（范围外疑似同类问题，交给质量工程师复核）。

试验数据：雪佛兰 Bolt EV 2017–2023、Bolt EUV 2022–2023，2026-09-13 取数，13 个召回活动、679 条投诉。

## 2. 流程（已用真实数据和 DeepSeek 跑通）

| 步 | 做什么 | 谁做 |
|---|---|---|
| 1 | 取数，记录来源地址和取数时间 | 代码 |
| 2 | 自动搭建本体：输入决策问题 + 字段目录（字段名和示例值），输出对象类型、身份字段、属性、关系、忽略字段、数据缺口 | 模型，1 次调用 |
| 3 | 核验本体：字段存在；同一对象类型在不同来源用同一套身份键；每个字段要么用上、要么写明忽略理由；事件 / 受影响对象 / 部件机制 / 信号四个角色齐全；每条关系在数据里真有连接；两个来源真的连上。有错误就把错误回传模型重做，错误数不再减少就停 | 代码 |
| 4 | 按本体把记录变成对象和关系；冒号分隔的部件路径自动建上下级 | 代码 |
| 5 | 范围查询：给定召回，算覆盖的车型年款、同部件（含上级类别）投诉，分成范围内 / 被同部件其他召回覆盖 / 所有同部件召回之外 | 代码 |
| 6 | 文本判断：投诉描述是不是同一个缺陷，yes / no / unknown，yes 必须附投诉原文片段，代码核对片段确实在原文里 | 模型，每 20 条一次 |
| 7 | 人工：看、改、确认本体版本；复核候选投诉 | 人（页面待做） |

试验代码已被正式代码取代并删除（`src/ontology_poc_generator/public_ontology.py`、`public_scope.py`，运行见 README"公开场景自动搭建本体"）。两轮试验的模型输出和报告留在 `experiments/nhtsa_auto_ontology/recorded/run_v1`、`run_v2`，下面第 3 节的数字出自这里；原始响应已并入 `examples/nhtsa/chevrolet_bolt_2017_2023.json`。

## 3. 试验结果

两轮，模型 `deepseek-flash`，第一轮 18 次调用约 10 分钟，第二轮 19 次约 9 分钟，时间主要花在逐批文本判断（串行，每次约 30 秒）。

### 自动搭建本体：可用

- 两轮都通过代码核验，都把两个来源连上了（7 个车型年款、5 个部件在两边都出现）。核心四类对象与人工写的参照答案一致：召回活动、车型年款、部件、车主投诉。
- 第一轮一次通过。第二轮模型多建了一个"单台车辆（VIN）"对象，投诉经它间接连到车型年款；代码核验指出"投诉和车型年款之间没有直接关系"，模型第二次补上后通过。代码核验 → 回传 → 模型修正这个循环有效。
- 模型自己列出 6 条真实数据缺口，例如召回只到车型年款、没有 VIN；召回正文写的年款区间可能比结构化字段宽；两边部件粒度不同。
- 第一轮本体漏了召回的 Summary 字段，下游文本判断因此只看到"可能无法正常展开"一句后果，把大量"安全气囊没弹出"的投诉判成同一缺陷。已加"每个字段要么用上、要么写明忽略"的核验，第二轮 Summary 被收进来。

### 范围查询：可用，换召回不用改代码

- 电池召回 21V650000（2020–2022 Bolt EV、2022 Bolt EUV）：同部件类别投诉 287 条，其中 43 条落在所有电池召回之外（2023 年款）。
- 安全气囊召回 21V517000：同类别投诉 23 条。
- 能力边界：查询只走直接关系；两跳路径（投诉 → 单台车辆 → 车型年款）现在靠模型补直接关系绕过。

### 文本判断：最不稳，不能直接当结论

| | 第一轮提示词 | 第二轮提示词（更严） |
|---|---|---|
| 投诉自带"起火"标记的 15 条，判为同一缺陷 | 13 | 11 |
| 没有起火标记，判为同一缺陷 | 112 | 22 |
| 安全气囊召回，范围外判为同一缺陷 | 5 | 2 |

- 第一轮把"召回配件还没到、车没出事"的投诉也算成缺陷发生；第二轮纠正了这类。
- 2023 Bolt EV 投诉 11600123（停车未充电时驾驶座下冒烟起火，所有电池召回都不覆盖）第一轮判 yes，第二轮判 no，理由是"召回写的是充电时起火，条件不同"。质量工程师会希望这条进复核。
- 结论随提示词措辞明显摆动，说明需要一份人工标注集来校准；在那之前，文本判断只作为"候选，待复核"展示。

### 数据注意

- 投诉接口对 2017 Bolt EV 只返回 4 条，明显偏少，可能接口不全；正式使用前对照 NHTSA 批量文件。
- 投诉的部件字段只有大类（如 ELECTRICAL SYSTEM），召回是完整路径，精确到部件只能靠文本判断。

## 4. 开发轮次

| 轮 | 内容 | 验收 |
|---|---|---|
| A | 把第 2 节 1–6 步做进仓库：本体用新格式 `public_ontology.v1`，不塞进 `OntologySpec`（它绑定合成链路，用户 2026-09-13 同意）；模型走现有 `model_gateway`；在线运行做成独立脚本，和 `check_recall_deepseek.py` 同一套约定 | 离线测试用录好的 NHTSA 快照和录好的模型输出，覆盖核验的每条规则（字段不存在、身份键不一致、字段遗漏、角色缺失、零连接、来源没连上）；在线脚本对 Bolt 快照跑通两个召回并出报告 |
| B | 文本判断标注集：从候选投诉里抽几十条，覆盖起火标记、召回配件问题、2023 年款、安全气囊，由用户或质量岗标 yes / no / unknown；用它比较提示词版本 | 每个提示词版本报告和人工标注的一致数与分歧条目；定下的版本号写进报告；是否达标由用户判断，不预设分数线 |
| C | 页面：看 / 改 / 确认本体（对象、关系、忽略字段、数据缺口）→ 选召回看范围结果和依据 → 复核候选投诉（沿用召回工作台的复核部分，顺带修 WB-01 筛选后详情错行）；静态站放一份录好的只读结果，完整流程在本机跑 | 浏览器走一遍：确认本体 → 选电池召回 → 看到 11600123 在"范围外"候选里 → 复核保存 |
| D | 换一个品牌或车型的部件召回，不改代码跑通；然后找质量岗试用 | 新数据从取数到范围结果不改代码；试用记录用时、漏项、人工修正 |

### A 轮完成情况（2026-09-13）

- 已做进仓库：`nhtsa_sources.py`（快照与取数）、`public_ontology.py`（核验、对象图、自动搭建循环）、`public_scope.py`（范围查询、投诉原文判断）、`scripts/run_public_ontology.py`、`scripts/fetch_nhtsa_snapshot.py`；新增 45 项离线测试，Python 3.11 与 3.13 都通过；全量回归 363 后端 + 101 前端 + 4 Sites 通过。
- 在线验收（`deepseek-flash`）：本体一次通过核验；电池召回 287 条候选，所有同部件召回之外 43 条，2023 年款座椅下起火投诉 11600123 在其中；安全气囊召回 23 条。与试验结果一致。
- 原文判断的稳定性，同一提示词 `public_defect_match.v2` 跑两次：电池召回 287 条中 261 条判断相同，安全气囊 23 条中 16 条相同；变化大多是相邻档（yes 与 unknown、unknown 与 no），yes 直接变 no 的 3 条。11600123 两次都判 no。B 轮标注集用来决定这一步怎么改。
- 与计划的差异：脚本测试放在单独的新文件 `tests/test_run_public_ontology.py`，避免同一提交里修改已有测试。

### B + C 轮完成情况（2026-09-13，合成一轮）

从场景出发，把 B 轮标注和 C 轮页面合成一件事：质量工程师在页面上的复核结论，本身就是校准模型初判的标注，不再单独做标注表。

- 页面"汽车召回范围研判（NHTSA）"是默认场景，读静态数据 `landing-page/public/data/nhtsa-bolt-review-pack.json`（由 `scripts/build_public_review_pack.py` 从 `examples/nhtsa/runs/2026-09-13-deepseek-flash.json` 与快照生成，`--check` 可验证未过时；打包时重算 13 个召回的范围，与报告不一致就拒绝）。
- 四步：看并确认自动搭建的本体 → 选召回（13 个，其中 2 个有模型初判）→ 按三类复核候选投诉（点选即保存，备注需先选结论）→ 看与模型的一致情况、下载复核结果。
- 从设计上避开旧工作台的问题：筛选后详情必属于可见列表（WB-01）；详情固定在视野内、手机上点选后跳到详情并可返回（WB-02/04）；没有"未保存草稿"（WB-03）；英文模式明示本页只有中文（WB-07）。
- 验证：后端 369 项、前端 109 项、Sites 4 项、三个 `--check` 通过；浏览器 1440×1000 用真实点击走完确认本体 → 标记 11600123 → 写备注 → 切换分类 → 刷新恢复；390×844 检查详情可见、返回列表、无横向溢出（该尺寸下工具点击未命中，改用页面内点击事件触发）。浏览器里发现并修掉一个重复 key 错误。

### 数据里新发现的漏检

刹车召回 18V576000 / 20V808000 的候选是 0 条，但投诉里有 11 条 SERVICE BRAKES。原因是两个来源的部件命名不同：召回写"SERVICE BRAKES, HYDRAULIC:…"，投诉写"SERVICE BRAKES"，对象对不上。本体核验能通过（其他部件连上了），所以代码核验发现不了这类漏检。页面已提示"0 条不代表没有同类问题"。

### 下一步

1. 部件命名对齐：让模型提出跨来源的取值对应（如"SERVICE BRAKES, HYDRAULIC"对"SERVICE BRAKES"），代码用数据核验每条对应真的能多连上记录，再进本体；验收是刹车召回出现候选。
2. 找一位质量岗在页面上复核（从电池召回的 43 条范围外开始），用下载的复核结果比较提示词版本。
3. D 轮：换一个车型跑通。

本轮不做：任意业务问题的通用本体平台（四个角色是为召回范围问题定的）；VIN 级判断；企业真实数据；后端云部署。
